# Rubric detail — block-state recovery routes

Relocated out of [`QUALITY-RUBRIC.md`](QUALITY-RUBRIC.md) section 5 by T156, which was at 5 characters of
DocBudgets headroom. Nothing here is a reviewer judgement criterion: these are the OPERATOR's routing notes
for a `block` that the harness authored rather than the reviewer. The state-code table itself stays in the
rubric, where selftest sub-gate 17t(doc) pins its header and where the R3 prompt still injects it verbatim.

## The state-code family

Not every `block` is a quality judgement. Where the block is **harness-authored** — no usable verdict could be read, or a verdict was read but must not be trusted — `review.ps1` tags it with an **ASCII state code** so the log tells you which failure you have and what to do about it. The first four codes below are the "no usable verdict" family; the later rows cover different moments and are marked as such, including the wall-clock timeout (§4), a non-zero exit paired with `pass`, and a stale-SHA verdict. The only remaining untagged blocks are the pre-existing baseline/diff/rubric resolution failures (Chinese fail-closed reasons, tracked as TD115) and reviewer-authored blocks — the latter carry the reviewer's findings, which are themselves the routing. All of them stay `block` — the gate never opens on an unclear verdict — but they route very differently. Within this family, match on the **state code**, never on the English prose (the prose is free to change; the code is the contract).

## When each state is raised

`[R3-VERDICT-WRITE-FAILED]` differs from the other four in *when* it is raised: the first four say no usable verdict could be read **from the reviewer**, whereas this one says the harness could not persist the verdict it had already decided. It is nonetheless a block state, and it **overrides a `pass`** — a verdict that cannot be persisted leaves no auditable record, and an unauditable approval is not an approval. Failing closed here matches the pre-existing behaviour, where an unwritable verdict path aborted the script outright.

The `[R3-NO-VERDICT-JSON]` route relies on the raw response preserved verbatim at `.review/<branch>.raw.txt` (the verdict file itself is overwritten with the normalized verdict, so the raw text is kept in a separate artefact). If that file write fails, the reason says so explicitly instead of pointing at a file that is not there.

That raw artifact is preserved *verbatim* precisely so you can see what the reviewer really said — which also makes it unsanitised reviewer-controlled text. Treat it as untrusted input: read it in an editor rather than `cat`-ing it into a terminal. (T69: the former excerpt-inlining and status-code anti-forgery pipeline was removed together with the mandatory-gate threat model it defended — with the review advisory by default, a forged opinion gains nothing enforceable.)

## 中文详解（既有面，逐字保留）

并非每个 `block` 都是质量判断（另有一条**不带码**的防御性兜底串，按现有分支不可达，故不列为契约）。**评审者跑完了、但从它的输出里读不出可用裁决**时，`review.ps1` 打一枚 ASCII 状态码，让日志自己说清是哪种故障、该怎么办。下表**前四行**才是这一族（其余行是另外几个时点/性质的状态，行内已注明）；下表前四态**只是这一族**，**并不覆盖全部运行态阻断**——超时（§4）、非零退出却报 pass、陈旧 sha、基线/diff/rubric 解析失败各有自己的英文 reason 且**不带状态码**。四态**一律仍 block**（裁决不明就不放行），但出路完全不同。其中 `[R3-OUTPUT-UNREADABLE]` 与 `[R3-NO-OUTPUT]` 易混却指向相反的排查方向：前者是**路径被占/读不了**（去查是谁占了那个路径），后者是**根本没写**（去查后端）——把读故障静默吞成「没写」正是本节要治的误导。**按状态码匹配，别按英文措辞**——措辞可改，状态码才是契约。其中 `[R3-NO-VERDICT-JSON]`（评审者干净退出、文件在、里面是散文）**可能**是分类器拒答/暂停，**也可能**是评审者把否定意见写成了散文、或后端吐了个无关错误——**先读另存的 `.review/<branch>.raw.txt` 原文再判**，别预设它与你的 diff 无关：若那段其实是评审意见，正确反应是**改 diff**，不是重跑到过闸为止；确属拒答/暂停时才走重跑 / 换第二后端 / 上人裁，**绝不是改卡措辞去骗分类器**，也绝不是 `--no-verify`。`[R3-BAD-VERDICT-JSON]` 则是「有 JSON 但读不出可用 verdict」的同类五支（whole output parses to no object / 缺 verdict / verdict 非字符串 / 枚举不符 / parsed but unreadable）。**运行期只强制 verdict 字段**（唯一决定放不放行的字段）；schema 其余约束（reasons 须字符串数组 / 禁额外字段 / sha·branch 须字符串）由 selftest 闸 ⑥ 在产出侧静态机检，不在此处运行期校验。`[R3-VERDICT-WRITE-FAILED]` 与前四枚的差别在**何时抬起**：前四枚说的是「从评审者那儿读不出可用裁决」，它说的是「裁决已经定了、但 harness 存不下来」。它同样是阻断态，且**会覆盖 `pass`**——存不下来就没有可复核的记录，而不可复核的放行不算放行。这与基线行为一致：从前裁决路径写不进去时脚本直接中止（非零退出＝不放行），故这里必须 fail-closed，不能因为「已经 catch 了异常」就顺势放行。

`[R3-NO-VERDICT-JSON]` 的恢复路由依赖**逐字另存**的 `.review/<branch>.raw.txt`（裁决文件本身会被规范化裁决覆盖，故原文另放一份）；**若另存失败，reason 会如实说明原文不可得**，不会指你去读一个不存在的文件。该原文正因**逐字保全**才有价值——这也意味着它是**未消毒的评审者可控文本**：当不可信输入对待，用编辑器看、别 `cat` 进终端。（T69：原摘录内联与状态码防伪造管线已随其威胁模型一并移除——评审默认是意见（T68），伪造一份意见换不来任何可执行的放行。）

## State codes and recovery routes

Moved here from `QUALITY-RUBRIC.md` section 5 by T153. **This table is the authority** - selftest
sub-gate 17t(doc) parses it here and requires a row for every `[R3-*]` code `review.ps1` can emit.
It is operator routing: the reviewer does not act on these, which is why it is no longer injected
into the review prompt.

| State code | What happened | Route |
|---|---|---|
| `[R3-OUTPUT-UNREADABLE]` | The verdict output path exists but could not be read as a file — it may be a directory, locked, or permission-denied. Distinct from "nothing was written": here something occupies the path. | Inspect the path named in the reason and whatever holds or replaced it, then re-run ship. |
| `[R3-NO-OUTPUT]` | Reviewer exited without writing a verdict file, or wrote one that is empty or whitespace-only. No review result was captured — a custom backend may have reviewed and simply failed to write the file. | Backend crashed / was killed, or a custom `ReviewCommand` never honoured `$env:REVIEW_OUT`. Fix the backend, re-run ship. |
| `[R3-NO-VERDICT-JSON]` | Reviewer **did** write output, but it holds no JSON verdict — prose instead of the schema. This **may** be a backend safety-classifier refusal or mid-stream pause; it may equally be an adverse review written as prose, or an unrelated backend error. | **Read the preserved raw output in `.review/<branch>.raw.txt` before acting; it decides which case you are in.** (1) Refusal/pause → re-run ship, these are often transient. (2) Recurring on a security-shaped diff → point `ReviewCommand` at a second independent backend (this gate is backend-agnostic by design) or escalate to human adjudication. (3) Actually review feedback → fix the diff; do not re-run until it passes. (4) Never reword the card to dodge the classifier. |
| `[R3-BAD-VERDICT-JSON]` | No usable `verdict` could be read. **Five emit sites, one class** (T283): the output opened an object and no complete object in it parsed — a truncated or half-written body, which is refused rather than salvaged, because an unterminated verdict's nested `axes` would otherwise be handed back AS the verdict and an axis carries a `verdict` of its own — or an object did parse and was missing `verdict`, carried a non-string `verdict`, carried a value outside the case-sensitive enum `{pass,block}`, or carried a field this harness cannot evaluate. The raw output is preserved for the no-parse site exactly as it is for `[R3-NO-VERDICT-JSON]`: a reviewer that quotes code while refusing carries a brace, and which of the two states that lands in must not decide whether its own evidence is kept. Runtime enforcement covers the `verdict` field only (it alone decides merge); the rest of `specs/verdict.schema.json` is checked statically by selftest gate 6, not here. | Backend emitted structured output that violates `specs/verdict.schema.json`. Fix the backend's output contract; for the built-in codex path, re-run ship. |
| `[R3-VERDICT-WRITE-FAILED]` | The verdict itself was decided, but the normalized verdict file could not be written, so this run left no auditable record of its own decision. Raised **after** the decision, and it overrides a `pass`. | Inspect the verdict path and whatever occupies or locks it (often the same cause as `[R3-OUTPUT-UNREADABLE]`), then re-run ship. |
| `[R3-REVIEWER-TIMEOUT]` | The reviewer subprocess exceeded the wall-clock budget (§4) and its process tree was killed — no fresh verdict exists for this run. A **budget signal**, not a quality judgement about the diff. | Retry once the reviewer/model recovers; for a legitimately slow backend or a genuinely long verification raise the budget (`-TimeoutSec` / `ReviewTimeoutSec`) — never bypass the gate with `--no-verify`, and never make the reviewer verify less (§4). |
| `[R3-NONZERO-EXIT-PASS]` | The reviewer wrote a `pass` verdict but its process exited non-zero — an approval from a run that itself failed is untrustworthy, so the gate blocks fail-closed. | Read the reviewer's own error output (ship log; raw artifact if present) to see why it exited non-zero; fix the backend/environment and re-run ship. |
| `[R3-STALE-VERDICT-SHA]` | The verdict carries a `sha` different from the reviewed HEAD — a stale or reused verdict from an earlier round, not a judgement of this commit. | Re-run ship so the reviewer judges the current HEAD; if it recurs, find out what keeps restoring or rewriting old verdict artifacts. |
| `[R3-TIMEOUT-BUDGET]` | **Startup announcement, not a verdict state.** Printed on the reviewer's startup line with the wall-clock budget that actually won the §4 precedence (`-TimeoutSec` > `ReviewTimeoutSec` > built-in 600s). It reports which budget the reviewer was given, never how the review ended. | Nothing to route — it is context. If the run later ends in `[R3-REVIEWER-TIMEOUT]`, this is the number that was exceeded: raise it (`-TimeoutSec` / `ReviewTimeoutSec`) rather than making the reviewer verify less (§4). |
| `[R3-ROUND-KEEP]` | **Console diagnostic, not a verdict state.** The round's verdict is also written to `<branch>.r<N>.json`, which the stale-verdict discard never removes (T145). | Nothing to route - the pointer file stays authoritative, and the siblings let a round be read against the ones before it. |
| `[R3-RUBRIC-SECTION]` | **Console diagnostic, not a verdict state.** Printed when this diff/card cannot trigger a conditional dimension (#13/#14/#15/#17), so it is not carried this round (T146). Names the omitted numbers. | Nothing to route - the dimension stays in this file and live downstream; undecidable triggers are always carried. |
| `[R3-FOLLOWUP]` | **Console diagnostic, not a verdict state.** Announced before the reviewer is invoked when a prior verdict on this branch, at a different sha, is carried into this round's prompt as data (T160/TD159). Names how many findings were carried. | Nothing to route - it reports that this round judges a delta rather than re-reading the diff cold. Absent on a first round, and deliberately absent when the prior verdict sits at the reviewed sha. |
| `[R3-INTENSITY]` | **Routing announcement, and on one class a decision.** Printed before the reviewer is invoked with `tier=<t> class=<c> source=<field or default>` (T301): the class `ReviewIntensityByTier` resolved for the tier this card's `allow_paths` compute. `adversarial` is today's behaviour and every degradation lands there; `advisory` runs one pass at the cheaper effort; `skip` writes a `routed_skip` verdict and no reviewer runs. A `floor=<why>` clause means a `skip` was raised back to `advisory`: `never-path:<p>` because the diff touches a path `ReviewSkipWhen` never lets a review be routed around; `ReviewGate=required` because the second-model verdict is the armed merge bar and a routed skip writes a `pass`, which would delete that gate rather than lower it; or `no-changed-paths` because the changed-path list came back empty, which is either an empty diff or a `git diff` that failed — and neither is evidence that this diff is cheap. | Nothing to route on `adversarial`/`advisory`. On `skip`, the verdict is a routed skip, not a review that passed - if you wanted a read on that diff, run `scripts/review.ps1` by hand or set that tier to `advisory` in `_config.ps1`. If the tier reads `?`, the card's `allow_paths` could not be computed from the base copy and the run correctly fell back to `adversarial`. |
| `[R3-RECORD]` | **Console diagnostic, not a verdict state.** A tracked, redacted record was appended to `.review/records/<branch>.jsonl` - card id, reviewed sha, verdict, model, effort. No reason text (T153). | Nothing to route. This is the audit trail ADR 0013 assumed already existed; the reason-bearing verdict body and the raw reviewer output stay gitignored. |
| `[R3-DIFF-VERDICT-REDACT]` | **Console diagnostic, not a verdict state.** A reason- or body-bearing field was dropped before the tracked record was written (T153). | Nothing to route - it means the redaction filter did its job. If you see it often, something upstream started putting diff text into the record payload, which must never reach version control. |
| `[R3-RAW-SAVE-FAILED]` | **Console diagnostic, not a verdict state.** Carries the OS-localized reason the raw-response artifact could not be written; the verdict is decided by `[R3-NO-VERDICT-JSON]` above, whose reason already states truthfully that the raw text is unavailable. Printed rather than posted because its wording is locale-dependent. | Read it in the ship log to see why the write failed (permissions, occupied path, full disk), then fix that and re-run ship. |
| `[R3-CARD-FROM-BASE]` | **Console diagnostic, not a verdict state.** The task card injected into the prompt was read from the pinned baseline commit, at the sha this line names - the same copy the ship's scope gate, the computed tier and any `arbitration:` ruling bind to (T290). | Nothing to route - it is context. It is the line that tells you a ruling or an amendment written on the base card was in front of the reviewer this round; if a verdict repeats one you have already answered on the card, check that the sha here is the commit your amendment landed on. |
| `[R3-CARD-FROM-WORKTREE]` | **Console diagnostic, not a verdict state.** The baseline carries no `specs/tasks/<branch>.md`, so the worktree copy was used instead (a branch-only card, or a project's first one). The ship's scope gate refuses a card the base does not have before any review runs, so this belongs to a manual review, never to a ship. | Nothing to route for a manual review. Seeing it during a ship means the base lost a card it should carry - register the card on the base branch before shipping, or the scope gate will refuse the ship anyway. |
| `[R3-RUN-STATUS-UNSET]` | **Console diagnostic, not a verdict state, and a bug report about `review.ps1` itself.** `Write-Verdict` was called with a `run_status` outside its enum, so the class was recorded as `tool_error` — the most conservative value. The verdict is unaffected: this never changes what was approved. It is printed rather than thrown because throwing here would kill the script before the fail-closed diagnostics above could print, which is the very failure `[R3-OUTPUT-UNREADABLE]` exists to prevent. | Nothing to route as an operator — it means a `Write-Verdict` call site in `review.ps1` was added or edited without giving it a class. Fix that call site; the run's own verdict still stands. |

## `run_status` — how the run ended, beside what it decided

Every state above is a `block`, and that is correct: the gate never opens on an unclear verdict. But `block`
alone cannot tell an operator **which** of two very different next moves to make — *fix the diff*, or *retry
the reviewer*. Since T188 the normalized verdict therefore carries a second, independent field:

- **`verdict`** answers *may this merge?* — still exactly `{pass, block}`, still the only field the consumer
  enforces, still pinned by selftest gate 17s against six hostile shapes. It did not gain a third value and
  must not: widening it would put every consumer at risk to describe a case none of them decide on.
- **`run_status`** answers *did a review actually happen, and if not, why not?* It is **producer-side only**,
  on the `routed_skip` precedent: `review.ps1` writes it, nothing reads it to decide a merge.

| `run_status` | Which states above produce it | What it tells you to do |
|---|---|---|
| `success` | A verdict was read cleanly — **for a `block` exactly as for a `pass`**, and for a routed skip. The class never encodes the quality answer. | Read the verdict. If it is a `block`, that is a real quality judgement: fix the diff. |
| `timeout` | `[R3-REVIEWER-TIMEOUT]`. A quota-exhausted reviewer lands here too — nothing in `review.ps1` can tell the two apart, which is why there is deliberately no separate `quota` value. | Retry once the reviewer/model recovers, or raise the budget (§4). Do not touch the diff on this signal alone. |
| `no_output` | `[R3-NO-OUTPUT]` and `[R3-STALE-VERDICT-SHA]` — nothing fresh was captured for **this** run, whether nothing was written or what was written belongs to an earlier sha. | Retry. If it recurs, find out why the backend never writes, or what keeps restoring old verdict artifacts. |
| `malformed` | `[R3-NO-VERDICT-JSON]` and all five `[R3-BAD-VERDICT-JSON]` emit sites. | Read the raw response first — it may be an adverse review written as prose, in which case fix the diff. Otherwise fix the backend's output contract. |
| `tool_error` | The harness or environment could not run a review at all: baseline unresolvable, no merge base, diff failed, codex absent, rubric missing, `[R3-OUTPUT-UNREADABLE]`, `[R3-NONZERO-EXIT-PASS]`. | Fix the environment. Nothing here is a statement about the diff. |

The class is written to the gitignored verdict body, to the round-indexed sibling `<branch>.r<N>.json`, and
to the tracked, redacted record `.review/records/<branch>.jsonl`. The round-indexed copy is the one that
matters for cost accounting: without it, a round record cannot separate *two quality rounds then human
adjudication* from *the reviewer timed out twice*, and an outage silently spends the two-round stop rule.

**`run_status` is not a merge input, and must not become one.** If you find yourself wanting to gate on it,
the deterministic gates are the merge bar (T68) — this field exists to route a human, not to open a door.
