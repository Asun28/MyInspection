# 房产巡检 App — 需求收口(Android 版)

版本:2026-08-14 · 状态:需求阶段,未开工
标记说明:**[定]** = 已决定 · **[待]** = 需要你确认 · **[验]** = 需要 spike 验证

---

## 1. 目标与边界

**[定]** 自用工具。唯一用户是我自己,不是产品,不给其他房东用。

**[定]** 解决的问题:自管房产时,按成熟模板逐项走查、拍照、备注,生成一份专业的巡检报告,并给出整改建议。

**[定]** 房客不是本 app 的用户。房客只收到一份 PDF,不签字、不登录、不提交任何东西。

### 明确不做(写死,防止范围蔓延)

租金与账务 · 房客筛选与背调 · 维修工单派发给第三方 · 房源广告 · 押金托管 · 任何账号体系 · 任何需要服务端的功能 · 多用户与权限 · 模板编辑器 UI

## 2. 平台与技术栈

**[定]** Android 手机,单设备。不做 iOS,不做 Windows,不做多端。

理由:现场真正好用的相机在手机上;单设备下「同步」可以合法地推迟;多端 + 无同步 = 数据孤岛,比任何单端都差。

**[定]** 纯 Web / PWA 已排除。三条硬伤:浏览器存储配额可被系统回收(照片是跨年证据,不能放这);Web Speech API 在 Android 上依赖联网;拿不到文件系统,无法把数据目录指向云盘。

**[待]** 原生 Kotlin + Compose,还是混合壳(Capacitor)?

- 会 Kotlin → 选原生。ghost overlay 用 CameraX 是标准操作,零不确定性
- 不会 Kotlin、Web 熟 → 选 Capacitor。UI 层以后能搬到桌面端
- 判断依据就是这一条,不用想太多

**[验]** 开工前先做一个 spike,一天以内:
> 打开相机预览 → 上面盖一张半透明的历史照片 → 拍下来存进 app 私有目录 → 能读回来显示

跑通 → 方案成立,后面全是体力活。
跑不通 → ghost overlay 降级为「拍完再比对」(两条路上都零风险)。

建议先在原生里跑这个 spike 当基准线。

### 以后的多端(不在本期)

真正做了同步之后再考虑。届时 Windows 端的角色不是采集,而是**模板编辑 + 报告归档 + 历史浏览**,和手机不重叠。

## 3. 巡检类型

四种全做。引擎共用,差别只在模板内容。

| 类型 | 场景 | 对照基线 |
|---|---|---|
| **Routine** | 租赁定期巡检(主场景) | 上一次 Routine |
| **Ingoing** | 入住条件报告 | 无(它自己就是基线) |
| **Exit** | 退租条件报告 | **该 tenancy 的 Ingoing**,不是上一次 Routine |
| **Annual Home Check** | 自住房年检 | 上一次年检 |

**关键约束:** Ingoing 和 Exit 必须成对。没有 Ingoing 基线,Exit 报告在押金争议里几乎没有证据价值。已经在租的房子补不回来,但下次换租客时能补上。

**排程:** 默认一年 4 次(约每 13 周)。这是提醒节奏,不是法律要求。

## 4. 模板与数据模型

### 层级

```
物业 → 巡检(类型/日期/tenancy) → 区域 → 房间 → 检查项 → 状态 + 照片[] + 备注 + 音频
```

### 硬性要求

- **检查项必须有稳定 ID**,历史对齐靠 ID 不靠名字
- **模板带版本号**,改措辞不改 ID,加项目给新 ID
- 主键用 **UUIDv7**(不是自增整数,以后同步时自增 ID 是死局)
- 每张表有 `updated_at`(UTC)和 `deleted_at`(软删除)
- 照片存文件系统,数据库只存相对路径 + 内容哈希;**不要塞 BLOB**

### 存储量估算

单次巡检约 15–30 张照片 × 4 次/年 × N 套房。加音频。三年下来是几个 GB 量级。

**[定,2026-08-19]** 照片与 PDF 的质量是两个独立设置：

- 新拍/新导入照片：`Low = 1280px/q75`、`Medium = 1920px/q82`、`High = 2560px/q88`、
  `Extra High = 4096px/q92`，默认 `Medium`；同一个持久设置由拍摄与导入在每次操作开始时读取一次并冻结，
  EXIF 转正后按比例缩小且绝不放大小图；只影响以后写入的照片，不重压已 finalize 的证据
- 每次导出 PDF：`Low / Medium / High / Extra High`，默认 `Medium`；`High` 作为证据归档建议档，不能用一个承诺的 MB 上限代替固定夹具实测
- 当前所谓“原图”是 EXIF 转正后保存的 JPEG，不是相机 RAW/DNG；不再额外保留一份未处理原图

### 评级体系 **[待]**

推荐:同一个 status 字段,允许值由模板类型决定。

- 租赁三种:`Good / Fair / Poor / N-A`
- 自住年检:`Significant defect / Maintenance item / Monitor`(NZS 4306 的缺陷分级思路)

### 「正常损耗 vs 损坏」 **[待]**

推荐:独立字段,**只出现在 Exit 模板**,且只对「与 Ingoing 有差异」的项目才要求填。

Routine 里每项都逼你判一次会拖垮流程,而且那时判也没意义。

## 5. 采集流程

### 拍照规则 **[待]**

推荐分两级,避免 100 项 = 100 张:

- **房间级:强制 1–2 张全景**。ghost overlay 主要用在这里,机位一致性在全景上价值最大
- **项目级:仅当状态非 Good 时强制拍照**

这样一次 Routine 约 15–30 张,现场走得完,而全景序列反而最能看出「这几个月房子变成什么样」。

### 导入照片 **[定,已降级]**

保留,但从「核心补救手段」降为可选(手机本身就是拍照设备了)。

两种形态:单项导入(补一两处)、批量导入 + 分配界面(选 20 张逐张指到项目)。

必须存:
1. **EXIF 拍摄时间**,与巡检时间分开存
2. **来源标记**(`camera` / `imported`)
3. **内容哈希**,防重复导入

哈希身份保持双轨：相机照片的 `content_hash` 覆盖缩放/编码后的最终 JPEG；导入照片仍以用户选择的原始
source bytes 作为 `content_hash`，另用 staged digest 校验派生 JPEG，质量档切换不得改变导入去重身份。

两个坑:**EXIF 旋转必须处理**(不处理导入后全是倒的);**复制不移动**,不动原文件。

导入的照片同样进入该项目的历史序列,可当下次的叠层底图。

### 草稿与完成 **[待]**

- 现场没网是默认状态,全程离线可用
- 草稿自动保存,粒度按房间
- **finalize 后原始条目只读**,可追加「补充说明」条目(独立时间戳)
- 导出 PDF 时把该次巡检的数据哈希写进页脚——成本近零,是自证「报告没被事后修改」的唯一手段

### 触摸优先

大点击区、单手可达、状态用大按钮不用下拉框、尽量少键盘输入(这也是语音和短语库存在的理由)。

## 6. 历史对比

**[定]** 范围收窄:**只做「拍的时候能看到前几次」**。

- 走到某检查项时,当前项旁显示上次的状态、备注、缩略图;可左右滑看更早几次
- **Ghost overlay**:取景时把上次照片作为半透明底图叠在预览上,对着它取景 **[验]**
- 数据模型区分两种引用:`previous_inspection`(时间上的前一次)和 `baseline_inspection`(该 tenancy 的 Ingoing)。Exit 模式默认显示 baseline

**不做:** 差异对比 PDF、只读历史报告查看器、照片自动比对。

**冷启动:** 前 1–2 次巡检这个功能是空的,要接受。

## 7. 语音输入

**[定,已简化]** Android 系统听写为主。质量好,支持离线语言包,零工程量。

**[定]** whisper.cpp 推到 v2。Android 上系统听写够用,不值得为了它打包 150MB 模型。

**[定]** 无论用哪个引擎,**原始音频都留下来**。识别会失败,失败时得有东西可回溯。音频存照片同目录,数据库存路径,报告里不出现。这也让以后换更好的模型时能重跑历史音频。

**[定]** 语音 + 预设短语库配合:80% 的备注是重复的("轻微磨损,与房龄相符"),短语库一点就有,比说话快;语音留给需要具体描述的那 20%("厨房台面靠水槽处 50mm 凹痕")。

## 8. 报告输出

**[定]** 输出 PDF。生成后丢进云盘文件夹,在电脑上阅读——**app 负责采集,阅读不必发生在 app 里**。

**[待]** 平行双语一份(中英并列),而不是双份单语。理由:争议发生时,双方手上是同一份文件本身就有价值。

- 模板固定项(房间名、检查项、短语库、建议库)预先双语化
- 自由文本保持原语言并标注

**[待]** 界面语言单语。为唯一用户做 i18n 框架是长期税(每加一个检查项写两份字符串)。建议英文,因为模板术语以英文为准(flashing、ground moisture barrier 这类写英文不易歧义)。

**[定]** 报告分两版:
- **房东版**:含 remediation 建议、紧急度分级
- **房客版**:客观描述 + 与房客相关的建议,不含内部判断

**[定]** 报告必须带免责声明:仅供一般参考,不构成法律、建筑或物业建议;标准与规则会变,行动前请咨询持牌从业者。

### 照片排版

每项缩略图内联 + 附录大图。几十张图的排版是真问题,PDF 生成放在原生侧比在 WebView 里打印稳定。

**[定,2026-08-19]** PDF 导出档位按用途控制照片采样，不改变报告内容、数据哈希或已存照片：

- Low：内联约 96 dpi、附录约 120 dpi
- Medium（默认分享）：内联约 120 dpi、附录约 160 dpi
- High（证据归档建议）：内联约 150 dpi、附录约 200 dpi
- Extra High：内联约 200 dpi、附录约 300 dpi

最终像素上限和 JPEG 参数以 80 照固定夹具、房间全景、铭牌小字、低光及高熵样本的真机结果为准；档位必须保持文件大小总体单调，但不承诺任意报告的绝对 MB 大小。

## 9. Remediation 建议

**[定]** 不做几百条规则库。自用场景下,人工写映射表不划算。

**[定]** 做法:一个 prompt + 一份「检查项 → 建议」种子对照表,用 LLM 生成。可以跑云端 API(自己的 key),生成建议时联一次网,可完全跳过。这不违背 local-first——数据始终在本地。

**[定]** 风险可控的理由:我自己看得出建议靠不靠谱,不会照单执行。但——

**[定]** 建议**只出现在房东版**。房客版只保留客观描述。

**[定]** 措辞边界:「建议联系持牌电工」安全;「更换这个开关」不安全。建议的定位是**提示 + 分级 + 建议找谁**,不是诊断 + 处方。

**[定]** 分级用 NZS 4306 的缺陷分类思路,不自创。

不做:成本估算(在 NZ 会很快过时)。

## 10. 合规与通知(NZ 特定)

### 通知生成 **[定]**

生成 48 小时通知文本 + 一键复制。**app 自己不发送**(会引入云依赖),由我手动发送后在 app 里记录。

送达存档必须存:
- 通知**全文快照**(渲染后的实际文本,不是模板 ID)
- 生成时间、预定巡检时间、送达方式(短信/邮件/信件)
- 送达时间戳,以及计算出的提前量(小时)
- 校验结果

### 校验规则 **[定]**

保存/发通知时阻断,不可关闭,不出现在设置里:

- 4 周内不得重复 Routine 巡检(**法律上限,不是节奏建议**)
- 通知提前量 ≥ 48 小时且 ≤ 14 天
- 巡检时间落在 08:00–19:00(寄宿公寓 08:00–18:00)
- **Ingoing / Exit 不计入 4 周限额**,校验器要按类型分流

最容易踩的场景:上次发现问题、想两周后回去复检。这时 app 必须拦下来并解释——即便双方同意,复检仍需 48 小时通知且不能突破 4 周限制。

### Healthy Homes 子模块 **[定]**

五项作为独立子模块,可单独出合规快照:加热 / 绝缘 / 通风 / 水汽侵入与排水 / 挡风。

日常巡检时的复核点:地板下绝缘未被破坏、抽风扇仍能运转、地面防潮层完好。

### 法规变更 **[待]**

规则应做成可更新的配置文件,不硬编码。local-first 下没有服务端推送,靠手动更新。

## 11. 数据、备份、隐私

**[定,ADR-0002]** 工作数据留在 app 私有目录；用户通过 Android SAF 自选加密备份目的地（Google Drive / OneDrive / 本地目录 / USB 等 provider）。ADR-0006 明确 supersede ADR-0002“全部活数据放 app-specific external storage”的具体落位：SQLite、设置、回执与恢复日志收紧到 credential-encrypted internal storage，只有体积大的照片/音频可放 app-specific external storage；app-private 边界、SAF provider 范围与本地数据库唯一真相源保持不变。这是可恢复的归档导出，不宣称双向同步，云 provider 失联不得影响巡检、finalize、历史或本地 PDF。

**[定]** 单设备 = 单点故障。手机丢了、摔了,几年的基线全没。**备份是 MVP 必需项,不是 nice-to-have。**

**[定]** 备份形态:整包导出 + 按物业导出，这是必须保留的产品范围。format v1 按物业兼容导出仍含整库 `db.sqlite`，必须明示“数据库包含全部物业、仅媒体按物业筛选”，不得获得物业隔离/可恢复回执或用于物业级交付。ADR-0006 只批准下一版按物业范围与逐表数据闭包，不是冻结格式的版本评审；实现卡仍须完成 version review。物业包须按 ADR-0006 的每表规则比较源/staging `(PK, canonical-row-hash)` 集合，并证明逻辑引用及数据库/媒体/manifest 双向完备；所有活跃模板/定义及已引用历史版本必须保留，内置短语须按锁定版本/hash 重建，确保零巡检物业也能开始新巡检。任一遗漏、多行、改值或无规则都失败。通过后按物业恢复以隔离快照替换当前 app 数据，不做隐式合并；当前有其他数据时先提示生成全量备份。

**[定,ADR-0006]** 恢复矩阵：v1 `full` 全验后可整包替换；v1 `property` 因整库 DB + 不完整媒体必须拒绝；完成冻结契约评审后的 v2 `full` 整包替换，v2 `property` 全验后以隔离快照替换当前 app 数据。旧 reader 拒绝 v2；新 reader 仅接受 v1 full 与 v2 full/property。未知 scope、未来格式或不支持 schema 一律拒绝，不得从标签猜测恢复语义。

**[定,ADR-0006]** 自动备份的目录树协议使用新 `.partial`，关闭重开全验后安全 rename，或复制到新最终文档并再次复核；手动 `ACTION_CREATE_DOCUMENT` 只依赖单个授权 URI，写完关闭后从同一 URI 重开全验，不假设 rename/copy。只有最终可读对象通过解密与 manifest/hash/size 校验才更新 Verified 回执；失败残留尽力删除，无法删除时提示用户且不得覆盖最近已验证状态。

**[定,ADR-0006]** 本地目录/USB 备份和本地包恢复可完全离线；Drive/OneDrive 等 SAF provider 是否离线可用由 provider 决定。provider 不可达、授权收回、低空间或后台密钥不可用，只影响该次备份/恢复，保留最近已验证回执并给出重试/重选/重新输入口令动作。

**[定,ADR-0006]** 自动备份仍为 finalize 后 + 每周，通过 Android SAF/DocumentsProvider 写入用户选择的目录；云 provider 对密文的后续传输由 provider 管理，不是 app-owned HTTP 上传。用户口令是跨设备恢复根；本机只保存由 Android Keystore 加密的口令信封供后台任务使用，不保存明文，信封不进入备份。Keystore 失效时自动备份暂停并要求重新输入口令，绝不降级成明文包。

**[定,2026-08-19]** 联系方式仍按租约结束后 12 个月一键清理。照片记录、哈希、PDF 和加密备份不按“保留几轮”删除；“保留几轮”只控制本机是否继续保留可重建的全尺寸照片字节。

本机全尺寸照片默认保留每个物业最近 **3 次已完成巡检**，用户可选 `1 / 3 / 5 / 10 / Always`。当前巡检、previous、baseline、手动保留项，以及未满足安全归档条件的照片永不进入清理候选。

安全归档条件必须同时满足：巡检已 finalize、PDF 已生成、照片的相对路径/哈希/大小已写入一份加密 `.mibk` 并从目标重新读回校验、已过 30 天宽限期、且不在上述固定集合。默认只预览并逐次确认；自动清理推迟到恢复/回填流程经真机验证后。清理后保留 DB 记录、内容哈希、PDF 和加密备份，不删除云端文件。

Google Drive、OneDrive、本地目录或 USB 通过 Android SAF 作为备份目的地；Google Photos 的“已备份”状态不作为可验证归档回执，v1 不接云账号、不做云端同步或云端删除。

**[未来设计,不在 v1]** 可增加付费托管云备份，但必须作为同一归档接口的另一种 provider，而不是把 S3 细节写进领域层。app 仍先在设备端生成加密 `.mibk`；服务端只在认证和订阅有效时签发短时上传/下载授权，S3 保存不含地址/租客名的 opaque object key 与密文。APK 不内置 AWS key，服务端不持有备份口令。云备份与多设备同步是两个产品，后者须另立方案。

**[定,ADR-0006]** 安全基线（个人项目、轻量）：数据库本身不做应用级加密，依赖 Android 文件加密、app sandbox 和设备锁；备份包必须认证加密。系统 Auto Backup/设备迁移排除全部 app 数据；不做云端账号、同步、遥测或 app-owned 后台 HTTP 上传。远程 remediation 是唯一 app-owned 联网点，必须显式触发、payload 最小化，离线失败不影响核心流程；自动 SAF 写入及 provider-managed 密文传输继续允许。

## 14. 生产可用性与非功能验收 **[定,2026-08-20]**

### 安全与隐私

- 图片导入只使用 Android Photo Picker/SAF，禁止申请全相册权限；app 不读取剪贴板，只有用户点 `Copy notice` 才写入通知文本。
- 密钥和凭据进入 Keystore 支持的本机加密存储；系统备份/设备迁移不得携带 app 数据；敏感文件只用临时只读 `content://` 分享。
- 本产品没有账号，故“账号物理注销”等价为 `Delete all local data`：二次输入确认后清除本机数据库、媒体、报告、设置、密钥、诊断、缓存与授权；用户自行保存的外部加密 `.mibk` 不删除且确认前明确说明。
- Remediation 是唯一联网点（仅指 app-owned HTTP adapter）：显式触发、最小 payload、HTTPS/平台 TLS、禁止 cleartext 和自定义信任绕过。自动 SAF 写入与 provider-managed 密文传输不属于 app 网络 adapter。无自有服务端时不得伪造 Timestamp+Nonce 防重放或额外引入 HTTPDNS；若未来新增可验证服务端/解析信任边界，必须先立 ADR 与威胁模型。

### 本地监控与发布证据

- 核心操作写入有界、脱敏、本机诊断事件；事件失败不影响业务。v1 不做 app-owned 自动遥测、Wi-Fi 诊断上传或远程秒级告警，用户只在明确确认后导出诊断包；这不禁止已授权的自动 SAF 加密备份。
- finalize/PDF/备份/恢复失败、连续 3 次备份失败、备份超过 7 天、完整性失败、恢复回滚和上次崩溃恢复必须在本机 1 秒内形成可操作状态提示。
- 崩溃记录按 Diagnostic registry v1 保存 `PREVIOUS_CRASH/FAILURE`、封闭 reason、格式受限 build id、封闭异常类型和最多 8 个安全帧标识；不保存 message、原始类名、行号、路径、URI 或业务值。每个 release 保留对应 Android mapping/符号证据与校验值，不把符号表、崩溃或日志自动上传。
- 发布前必须完成权限拒绝、飞行模式、进程死亡、备份/恢复、数据清除、崩溃恢复和临时分享授权矩阵。
