# Eval：能力完成度方法论（opt-in）

> 脚手架的闸门答「这次改动对不对」（worktree/TDD/Codex/CI 都是单卡/单 diff 级）；
> eval 方法论答「**整个产品各项能力，哪些 DONE、哪些 NOT-DONE**」。**本仓不自带 runner/套件**——
> 工具无关（L26）：标准与四维在下，具体 runner/套件由**下游自行接入自己的 CI**。

## 确定性闸 vs 上游 LLM-judge（judge 永不当闸）
- **只收确定性 eval**：每条 = 能机检 exit 0/1 的命令（L25）。
- **模型主观质量评判**（LLM-judge、视觉打分）**留在上游**——非确定、要联网，**绝不进闸**；只帮上游写/审 eval。
- **行为型红队/对抗安全**走排期审计，不混进完成度闸。

## 四个维度
| dimension | 评什么 |
|---|---|
| `frontend-behavior` | 用户操作→页面行为（关键旅程走得通） |
| `backend-mcp` | 后端/MCP 契约：稳定、幂等、跨调用一致 |
| `security` | 静态 SAST、依赖审计、密钥扫描（作闸）；行为型红队作排期审计 |
| `functional` | 功能黄金集：输入→输出比对期望，回归不退化 |

## GROW：缺陷类回归回流
每个逃逸到产线的 bug → 下游补一条回归 eval，令同一缺陷不可复发（镜像经验系统 `enforced_by` 机械守卫）。

## 落地
下游按上述标准自建最小基线（每维 1 条起步，YAGNI）+ 自接 CI；本文件只装方法论。
