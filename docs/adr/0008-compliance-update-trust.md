# 0008 — 合规规则更新的来源信任与版本策略

日期：2026-09-08 · 状态：accepted（用户已批准设计；本卡交付仍须正式 R3 与合并）。

本记录属于 T4-COMPLIANCE-UPDATE-TRUST，补充 ADR-0004 的更新信任边界。用户决策已记录于文末；前置卡正式通过 R3 并合并后才解除本项依赖，不覆盖 ADR-0004 的用途限制。

## 背景与证据

需求 §1 明确唯一用户为房东本人；§10 要求手动更新、规则不可编辑或关闭。`ComplianceConfigLoader.load` 只证明 bytes 与外部 expectedSha256 一致；摘要来源不由 loader 证明。无效 override 回内置、内置无效抛错。schemaVersion 1 无发布序号、密钥或过期字段；effectiveDate 解析不是生效时刻授权。sourceRefs 是法规引用，不是发布者身份。
核验日期 2026-09-08：[Android Signature](https://developer.android.com/reference/java/security/Signature) 列出 SHA256withRSA 从 API 1 支持；本仓 minSdk 26。使用平台 JCA 验签，无新增运行时依赖；平台兼容表不代替 API 26 与实际目标设备的验签向量测试。[Android 应用签名文档](https://developer.android.com/studio/publish/app-signing) 说明更新身份依赖应用签名密钥，自管密钥丢失可能失去原应用更新能力。以下策略是项目设计选择，不是官方发布服务的既有事实。

## 批准决定与备选

| 方案 | 判断与代价 |
|---|---|
| 单公钥离线数字签名（采用） | APK 内置信任根，导入时验证发布者授权的字节；运输不承担认证。需要维护私钥和可信 APK 更新链 |
| 独立可信摘要 | 摘要须经独立认证途径取得，目前无该途径证据。每次随 APK 内置允许摘要可成立，但每个规则版本都要升级 APK；人工抄摘要不作为默认流程 |
| 同包或同下载点的 hash | 拒绝作为身份验证。攻击者修改阈值并重算 hash 仍一致；单独一个摘要文件不自动产生独立信任 |

用户最终批准每次规则内容与法规依据；Agent 可整理候选，不能自行成为发布者。规则专用私钥在用户控制的发布电脑离线保管，与 APK 签名私钥分开；私钥、口令不进 APK、仓库、规则包或任务证据。由用户在该电脑执行签名；本卡不生成或读取密钥。
首个 release APK 从该受控电脑经 USB 安装，规则包也从该电脑经 USB 复制后由 SAF 选择；后续 APK 用原应用签名身份更新。USB 本身不是认证，信任建立依赖受控电脑、正确构建与本人安装。网页、聊天、镜像上的规则包只能是运输副本，仍须同样验签；不创建任何服务或网络更新。

## 包边界与兼容

每个 APK 固定一个规则公钥及单调递增的 trustEpoch、minimumRelease、内置规则完整身份；包不能携带新公钥、更改算法或授予自己新代次。RSA 3072-bit、指数 65537，JCA `SHA256withRSA`（PKCS#1 v1.5），公钥使用 X.509 SubjectPublicKeyInfo DER；不自写密码算法、不指定设备 provider。trustRootId 定义为 APK 内该公钥确切 SPKI DER 字节的 SHA-256，以固定 64 位小写十六进制保存、比较和显示；预检与发布证据中的规则公钥指纹均用此身份。
采用有界、不压缩的二进制外层，保留现有 JSON 原始字节，避免改冻结 schema 或复用 inspection canonical。布局按序唯一确定：ASCII `MI-RULE1`（8 字节），trustEpoch（8），release（8），effectiveDate（10），expiresOn（10），payloadLength（4），payload（N），signature（384）。整数为大端非负值，epoch/release 取 1..Long.MAX_VALUE；长度取 1..65536。总长恰为 432+N，最多 65968 字节，禁止尾随数据、截断、溢出、其他 magic 或变长签名。
日期严格为 ASCII YYYY-MM-DD、公历真实日期、年份 0001..9999；expiresOn 的唯一无期限标记是 `0000-00-00`，有期限时须大于 effectiveDate。签名覆盖从 magic 到 payload 末尾的全部原始字节；signature 自身不在签名输入中。全包 SHA-256 用于确认绑定，已验签内容段 SHA-256 用于版本身份；均不单独证明发布者。
先有界读取并验证固定格式、APK epoch、公钥签名，再解析 JSON。JSON 限容器嵌套深度 16（根对象为 1），键不超过 64 个 Unicode 标量、字符串不超过 2048 个、任一数组/对象成员不超过 64；严格 UTF-8，拒绝重复键、未知字段，并调用现有 loader 的领域校验。外层 effectiveDate 必须与 JSON 完全相同，timezone 仍为 Pacific/Auckland，用途只能为当前批准的 inspection；有效签名也不能启用 work-check。限额边界与旧内置配置均纳入测试。
禁止直接导入裸 JSON 或旧 digest-only override；不把既有 override 自动升级为可信。schemaVersion 1 继续使用原 loader；新 schema 必须另走版本评审及旧配置兼容向量，本卡与依赖导入卡均不修改它。当前 FrozenPaths 列表尚未登记 compliance，不代表可绕过原卡承诺的冻结与版本流程。

## 版本、日期与使用规则

APK 的 trustEpoch 是唯一代次权威，只接受同代次包。同代次维护最高已激活 release H 与内容身份，准入下限为 max(H, minimumRelease, 内置 release)。低版本拒绝，同版本同内容幂等、同版本不同内容拒绝；新版本即使规则内容回到旧值也须显式重新批准和签名。内置版本等于 H 时也须与保存的身份一致。
APK 升级同代次先比较已保存 trustRootId 与当前 APK 公钥身份；不相同即阻断，不能用更高内置 release 覆盖，也不能按首次安装重新初始化。相同时保留 H；内置 release 提高时，先全验内置配置，再将它与提高后的 H 一起提交；已有更高有效 active 则保留。新版内置 release 不得小于 minimumRelease。仅更高代次可接受新 trustRootId，并与新内置配置原子初始化；旧代次全部失效、旧 H 不沿用，初始化失败则阻断而不能继续用旧代次。泄露密钥写入 Long.MAX_VALUE 也不能卡死合法换钥。APK 代次低于已记录代次时阻断相关操作；普通包无权复位 H、更换根或改变代次。
每次激活、启动和规则支持的业务操作均重判时间；规则须已对 Auckland 当日生效，并覆盖拟进行巡检的 Auckland 日期。未来生效包拒绝，届时重新导入，不做定时自动切换。有 expiresOn 时采用独占上界：当日或目标日期 >= expiresOn 即不可放行。无期限不意味着法规永远有效，不自动添加无依据的固定过期周期。
保存本机已观察最高 Auckland 日期；日期倒退即标记时钟异常，保留数据但阻断依赖合规的操作，纠正到不小于该日期后重试。误调到远期的恢复流程是：先在系统设置纠正日期，由发布者提供更高 epoch 的可信 APK，在新代次初始化时由用户确认显示的 Auckland 日期，以该日期重建水位并全验内置规则；拒绝确认则保持阻断。所有新代次初始化均走此确认，普通包或同代次 APK 无权复位日期。此机制不证明真实时间，也无法识别首次安装时就错误的时钟。
不可用规则不得生成“合规通过”：阻断巡检排期/通知生成、巡检保存或 finalize 中既有的合规放行步骤。继续允许查看、采集并保存照片/备注等原始证据、导出既有只读报告、备份与恢复入口；不把配置故障扩大成证据丢失。没有证据证明法规最新时不得显示“最新法规已验证”。

## 确认、原子激活与恢复

inspect 只读 SAF 源到应用私有受保护 staging，一次有界读取后快照不再可变；展示发布身份、公钥指纹、epoch/release、日期和来源引用。确认绑定 staging 全包 hash、当前 active 身份、APK 信任策略身份及该次预检，不绑定可变 URI 路径。取消清除预检并恢复焦点，旧确认不能公开构造或跨会话使用。
activate 只使用已确认快照；源 URI 后来换内容不影响快照，重新选文件须重新预检。提交前复验快照 hash/签名/领域/日期/当前策略与 active 身份；并发激活串行化，旧确认失效。旧确认重放返回已完成或失效，不做第二次写入；active 损坏但受保护的 H/内容身份仍可验证时，新 inspect 与新确认可用同 release、同保存身份的有效包进行修复性原子重写，H 不降低。若 H/身份也不可验证则进入恢复阻断态，不能把修复当首次初始化。
active 包、H/对应身份、epoch、trustRootId 与最高观察日期作为单个受保护提交状态原子发布；持久化完成并重读全验后才回报成功，不先写 H 再写 active。复用已有私有持久化与恢复能力，具体磁盘算法由实现验证，不新增 DB 表。无法证明状态完整时不给业务使用部分字段；新协议状态缺失或损坏 trustRootId 同样阻断，不借旧格式升级分支绕过。
启动恢复在合规业务装配前执行；只接受已完整提交的状态，staging 不因“签名有效”而自行激活。初始化采用下节明确的 Keystore 标记/状态矩阵，不使用安装时间、versionCode 或“没有配置文件”单独证明首次安装。目标设备故障注入须覆盖关闭、同步、替换和回读失败。

### 初始化证据与状态机

Android 信号取自成功加载的 `KeyStore.getInstance("AndroidKeyStore")` 的 `aliases()/containsAlias()`，不是可随备份复制的 SharedPreferences。只识别本功能前缀 `compliance-state-v1-e`；完整 alias 为前缀 + 无前导零的十进制 epoch + `-` + 64 位 trustRootId。它是该代次状态加密用的不可导出 AES-GCM key，同时标记该代次初始化已经开始；复用 LocalSecretBox 的 alias/version/purpose 隔离，不复用规则签名私钥。此前缀下畸形 alias、同 epoch 多根或 key 类型/用途异常均阻断，不跳过。枚举/读取失败、锁定、key 失效属于不可用，不得转换为“没有标记”；合规状态失败不能通过重新输入备份口令复位。
依据：[Android Keystore](https://developer.android.com/privacy-and-security/keystore) 描述应用独享 key、不可导出性及 alias 枚举；[KeyStore API](https://developer.android.com/reference/java/security/KeyStore) 区分存在查询与异常。状态文件与 staging 使用 AppStoragePolicy 的 internal credential-encrypted/no-backup 路由；[getNoBackupFilesDir](https://developer.android.com/reference/android/content/Context#getNoBackupFilesDir()) 排除自动远程备份，本应用导出/恢复另显式排除信任状态。以上 API 已核验（2026-09-08），不把它们描述为防 root 删除或防整机快照回滚的硬件单调计数器。
初始化顺序固定为：全验当前 APK 内置包和下限 → 用户确认当前 Auckland 日期及将使用该 APK 内置规则 → 创建当前 epoch/root alias 并重查成功 → 用该 key 原子提交并重读初始状态（H=内置 release，最高日期=确认日期）。初始化之前不能接受手动 override。旧代次 alias 在新状态提交成功前不删；保留的 alias 取最大 epoch 作为本机代次标记 M。新代次 key 创建后状态未完成即中断时，M 已提高，旧代次不再可用；明确阻断并要求更高 epoch 的可信 APK 修复，不假称所有初始化中断都能自动恢复。

| 可观察证据（先查异常，再查 marker M 和新协议状态） | 判定与转移 |
|---|---|
| Keystore 或状态目录不可读、设备未解锁、alias/key 异常 | 不可用/可重试解锁；不初始化、不删标记、不修改 H |
| 无本功能 alias，且无新协议状态或 staging | 允许上述一次初始化。首次安装和未使用新协议的旧版升级走同一入口；旧 digest-only 文件仅忽略，不用它证明安装版本 |
| 无 alias，但存在任一新协议状态或 staging | 孤立状态，阻断；不重新生成 key 或认证旧状态。保留原设备数据，恢复途径是通过既有加密备份流程在新的可信安装恢复业务数据，不自动清数据 |
| M 存在，当前 APK epoch < M 或同 M 不同 root | 拒绝 APK 代次/根；禁止初始化，即使状态损坏或内置 release 更高 |
| 当前 epoch=M/root 一致，且该 key 认证出完整已提交状态 | 按版本/日期规则继续；状态中的 epoch/root 必须匹配 marker，不能采用低代次旧提交 |
| 当前 epoch=M/root 一致，但状态缺失/损坏/认证失败（含首次初始化中断） | 阻断，不借初始入口清空 H/日期；可验证 H/身份仍在时仅允许前述同身份修复，否则使用更高 epoch 的可信 APK 初始化 |
| 当前 APK epoch>M | 这是已批准的可信 APK 代次升级；可执行上述初始化，即使旧代次状态损坏。新 alias 创建前失败不改 M，创建后失败按当前 M 缺状态分支阻断 |
| 用户清数据、卸载重装或迁移后再次启动 | 按实际 alias/文件组合走上表，不猜 Android 是否清除了两者。两者皆无即新安全生命周期，只保证当前 APK 下限；一方残留则阻断，完整保留则继续 |
| 业务备份恢复 | 不写 alias、H、日期或信任文件；已有安装沿用本机状态，新安装先完成初始化再恢复业务。若错误包含新协议信任文件，拒绝该信任输入并报告，不认证成恢复状态 |

全部 alias 与信任文件同时消失时，本地无法区分第一次安装、清数据或整套安全状态被删除；本方案明确不提供这种情况下的历史反回退保证。单独丢失状态文件时仍有 Keystore marker，必须阻断而不伪装首次安装。这是已批准重装/清数据保证范围的具体化，不是用 UI 的“我是首次安装”选项代替证据。

| 场景 | 决定与恢复行为 |
|---|---|
| 候选伪签名、同源假摘要、未知钥/epoch、格式或领域错误 | 拒绝候选，保留当前配置；当前配置仍须通过使用时检查，不能借拒绝路径放行 |
| 未来生效、已过期、旧版本、同版本异内容 | 拒绝；显示具体原因和重新取得有效包的动作，不提供“仍然使用” |
| 选取取消、SAF 拒绝/撤权、超限流 | 取消或拒绝，本次不改 active/H；不泄露原始路径/异常文本 |
| 预检后源替换、staging 被改、策略/active/日期变化 | 仅源替换不改已确认快照；其余条件失效则拒绝并要求重做预检 |
| 写 staging 中断、提交前中断 | 忽略未提交候选，重新检查旧提交；不将候选版本计入 H |
| 原子发布中断、发布成功但回执丢失 | 启动只选完整旧状态或完整新状态；若新提交已完成则重读显示它，重复确认无二次效果 |
| active 损坏或已失效 | 仅可恢复到同 epoch、未撤销、日期有效且满足下限/同版本身份的完整配置；内置也逐条检查。无合格配置则阻断，提示重新导入相同有效版本或更高版本/可信 APK |
| 旧 digest-only override | 不认证、不自动迁移；仅按上述无 marker/无新协议产物入口初始化内置规则，不需要猜测旧安装版本；任一新协议 marker 或产物存在即不得走此入口 |
| 正常轮换 | 新 APK 升 epoch、替换公钥并原子保存新 trustRootId，携带当日有效的新代次内置规则；同 epoch 异根一律拒绝（即使内置 release 更高）。旧包全部拒绝，无双钥宽限；旧客户端拒绝新代次包，须更新 APK |
| 规则私钥丢失/泄露、错误规则撤销 | 停用旧钥；通过同应用签名身份的新 APK 升 epoch 换规则钥并装入修正版内置规则。包不能撤销根；错误未泄钥时可更高 release 修正，但强制撤销须 APK 策略更新 |
| 应用签名私钥丢失/泄露或发布电脑失陷 | 单规则钥轮换不足；停止信任该发布链，需独立事件处置与重新建立首次信任。不得宣称现有渠道仍可安全恢复，不自动卸载或清除用户数据 |
| 重装、清数据、备份恢复 | 新安装只保证 APK 自带下限，历史 H/日期可能丢失。规则状态不进入用户数据备份；恢复不能覆盖现存本机信任状态，恢复的排期以本机有效规则重查；root/旧整机快照回滚不在反回退保证内 |

## 保证范围与交付责任

离线设备收到新版 APK 前无法知道撤销或法规变化；签名只证明被信任钥签过内容，不证明内容正确、时钟真实或已取得最新规则。威胁覆盖替换/伪造包、同源摘要伪装、重放、确认换包、解析资源耗尽与激活中断；不声称抵御已控制发布电脑、APK 签名钥、root 设备或被回滚的全部本机状态。
导入卡 owns 验签、版本/日期状态、inspect/activate、恢复及生产接线；:core/update 暴露经验证的当前规则或明确不可用原因，业务和 UI 不取得 raw loader。MainActivity 装配唯一规则服务，启动与业务使用时走同一服务；不能只保护设置页。若实际调用者/备份接线超出该卡 allow_paths，开工调查时先修订范围，不能跳过调用者验收。
实施/发布阶段须提供真实公钥、签名 release APK、内置包和离线签名产物。导入卡真机验收记录两种公钥指纹、APK 构建身份、受控电脑到设备的首次安装过程、有效签名包与换钥演练。记录公开指纹和结果，不记录私钥或口令；这些是交付证据，不倒填为本设计卡已完成。
