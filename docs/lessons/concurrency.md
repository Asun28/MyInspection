# 按需经验：共享检出并发协作（Tier 2）

> 按需层：在多会话/多 agent 并行操作**同一个 git 检出**（主检出或任何被多方共用的工作树）时由 `lessons` skill 触发加载。
> 源自 `docs/lessons/LEDGER.md` 的精选晋升；勿在此另起真相源，账本变更后同步本页。

## 核心原则：worktree 隔离是解药
- git 的 HEAD / 索引 / 工作树是「每个 worktree 一份、跨进程共享」，不是「每个会话一份」——git 没有会话隔离；谁最后 `checkout`，谁就决定了此后所有并发进程 `commit` 的落点。两个会话交替 `checkout`/`commit` 时，一对本该成对的提交（如新功能与它依赖的修复）可能被拆到两条分支，各自单独跑都不绿。
- 并行 agent/会话一律各自 `git worktree add -b <id>` 隔离：编辑、跑测试、提交都在该 worktree 内完成；只在落地时用一次简短 `git merge --no-ff <branch>` 触碰共享主检出（冲突即 `--abort`，报告分支就绪）。开工前先 `git worktree list` + `git status --porcelain` 确认没有别人正在同一个检出里干活。
- 绝不在共享主检出上 `git reset`、绝不跑长编辑会话——那是共享可变状态，一次 `reset`/长会话就可能撞上其他会话中途的 commit/merge/revert，令自己已验证的提交被意外撤销、或把别人的进度带偏。已丢失的已验证提交可从 `reflog` cherry-pick 恢复到新 worktree 分支。

## 共享主检出上不可避免要提交时
- 裸 `git commit` 会把其它会话已 stage 的改动一并卷入——一律用 pathspec 限定式提交（`git commit -F <msgfile> -- <path…>`，敏感/多行消息走文件避免命令扫描误拦）。
- 新建的未跟踪文件必须先 `git add <path>` 使其被跟踪，pathspec 限定式提交才能命中它（命中后仍只提交该路径，不会卷入其它已 stage 文件）。
- 提交前 `git status --short` 核对一遍，确认不会误带别的会话正在写的文件（例如别人半成品的任务卡）。

## 破坏性动作前先判断是否安全
- 已落错分支的提交按「先加法、后（谨慎）减法」处理：先 `cherry-pick` 到它该去的分支，并用 `git log`/`git show` 核实内容确已落地（加法、非破坏性）；原分支上多出的那个提交默认**不动**——直接从 base 另开一条干净分支继续，让错放的分支自然作废。
- 只有同时满足「该分支从未推送（`git ls-remote --heads origin <branch>` 为空）+ 工作树干净或已 stash + 已用 cherry-pick 核实内容确实在别处可达」这三条，才可以用 `git checkout -B <branch> <base>` 复位分支指针；任一条不满足、或分支已推送/共享，一律改走 revert + PR，不复位指针。
- 永不 `reset --hard`、永不对共享分支改写历史；`reflog` 只是兜底，不是执行破坏性操作的许可证。

## 大 PR 撞并发 churn（改写共享 append-only 文件时）
- append-only 真相源（如经验账本、技术债追踪表）被多个活跃会话同时追加/合并时，一个大 PR 反复冲突：把小而独立的部分（如纯新增条目）拆成独立 PR 先落，避开大 PR 的冲突面；等 churn 停（观察远端分支 SHA 连续几次不再变化）再 rebase。
- `rebase --onto` 前紧邻着重新 `fetch`——用陈旧的远端引用做三方合并基线，会把并发新增的内容当成「不存在」，静默当删除处理丢弃掉，而不是报冲突。
- force-push 前用集合差核验没有并发新增物被吞：拿远端一侧的条目/卡片 id 集合与本地一侧比较，「远端有、本地没有」的差集必须为空。
- 人工手填、非机检唯一的自由文本 id（如经验编号）在并发环境下可能撞号；撞号就把那部分拆成独立 PR，在最新基线上重新申领下一个空 id，而不是在同一个大 PR 里死磕合并冲突。

## 别信记录自陈的完成态
- 任何「状态」字段（任务卡 status、进度标记等）都是自由文本，由撰写者手填，没有机检约束它与 git 的真实状态（分支是否存在、PR 是否合并、账目是否结清）保持一致。多会话并发写作环境下，一份草稿完全可能带着乐观或占位的状态字面量、却从未真正落地。
- 捡到一份看似「已完成」的记录（尤其来自未提交/未跟踪文件，或来源不明）时，先用 `git branch -a` / `git log` 交叉核验它自称的分支/PR 是否真实存在过、对应账目是否真已结清，而不是直接采信记录自己的状态声明；状态只有在与这些外部真相源一致时才可信。
