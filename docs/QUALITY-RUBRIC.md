# Review Rubric (R3 second-model review decision standard) · 评审 Rubric

> EN: The 17-dimension rubric the R3 second-model reviewer (currently codex, via `scripts/review.ps1`) judges every PR against — six must-block dimensions (scope, hard boundaries, frozen contracts, license, originality, missing/fake tests) plus eleven should-flag ones — with a pinned adversarial stance: when uncertain, block. This file is injected verbatim into the reviewer prompt, so it IS the merge-gate decision standard — and `review.ps1` reads it from the **base commit** rather than from the branch under review (falling back to the worktree copy only when the baseline carries no rubric at all), so a diff cannot weaken the standard it is judged by. Since T288 the same holds for `scripts/review.ps1` itself, with no fallback: both ship legs run the base commit's copy and announce `[R3-REVIEWER-FROM-BASE] sha=<base>`, so the evaluator sits outside the loop it judges (`docs/HARNESS-REVIEW.md`) and a card that repairs the reviewer is reviewed by the base copy, its repair serving the next card.

> **English-first / bilingual** — this file is injected verbatim into `scripts/review.ps1`'s reviewer prompt **and** is edited per-project, so it is the one steering file an English-only team must be able to read and maintain. The Chinese is kept alongside for the original audience. Reviewers should emit their `reasons` in **English** (they are posted to GitHub PR status/comments).
>
> **Motivation** (Anthropic, *Harness Design for Long-Running Agentic Applications*): a reviewer agent naturally tends to **confidently praise mediocre output**, and after spotting a real problem **talks itself into "this is no big deal"** and lets it through. Countermeasure: upgrade "pass/block" from **free judgment** to **judgment against an explicit rubric + mandatory evidence**, and pin the reviewer's stance — **when uncertain, block; never find excuses for the author.**
> 动机：评审型 agent 天然倾向自信地夸奖平庸产出，并在发现真问题后说服自己「这没什么大不了」而放行。对策：把判定升级为「对照明确 rubric + 必须给证据」，并钉死立场——**不确定即 block，绝不替被审方找台阶。**
>
> Authoritative source of the standard fed to the reviewer; change decision dimensions here first. Ships downstream — projects extend §1 with their own hard-boundary / invariant clauses.
> 本文件是权威来源，改判定维度先改这里；随模板下发，下游按自己的「硬边界 / 关键不变量」补充 §1。
>
> **R3's nature — a deliberately accepted *non-deterministic* gate** · R3 的性质（有意接受的非确定闸）: R3 is a **second-model adversarial review that replaces the human approver** — NOT an "LLM-judge quality score". The scaffold's "deterministic gates only / a model judge is never a gate" axiom (see `docs/EVAL.md`) bans **subjective quality scoring** as a gate; it does **not** apply to R3, because replacing a human reviewer is inherently non-deterministic (a human approver isn't reproducible either). Trade-off: the verdict **can differ run-to-run**. **Role (T68): advisory by default, with one computed exception** — with `ReviewGate` empty in `scripts/_config.ps1` the merge bar is the deterministic gates and this review only reports; since T242/TD248 it does INVOKE it, advisory, for any card declaring `review_gate:` itself. The exception (T277 / ADR 0016 item 4) is per-card and computed, never a global switch: on a **Tier-S** card an axis-`spec` block stops the ship with `[R3-SPEC-BLOCK]` before any merge. A `standards` finding blocks at no tier, and neither does a timeout or an unreadable/malformed verdict — those carry no axes at all. Measured when that landed: 243 of 243 archived cards, 4 of 4 live cards and `specs/tasks/_TEMPLATE.md` all declare the field, so here that is effectively every ship - `ReviewSkipWhen` (T104) is the existing lever if that cost matters; run `review.ps1` manually whenever a second opinion is wanted, and a spurious block costs nothing but the read. Set `ReviewGate = 'required'` to restore the legacy mandatory gate (block stops ship; verdict + reasons persist in `.review/<branch>.json`).
> R3 是**第二模型对抗评审代替人工审批**，不是「LLM 质量打分」。脚手架「确定性闸 only / model-judge 永不当闸」禁的是**主观质量分**当闸，**不约束 R3**（代替人工 reviewer 本就非确定）。代价：裁决**跑跑可能不同**；**角色（T68）：默认意见模式 + 一条按卡计算的例外**——`ReviewGate` 留空时合并闸=确定性闸、本评审只报告；T242 起，卡自己声明了 `review_gate:` 的仍会**跑**一遍（只报告、不拦合并），误 block 的代价只是读一遍意见；例外（T277 / ADR 0016 item 4）按卡计算、非全局开关：**Tier-S** 卡上 `spec` 轴 block 在合并前以 `[R3-SPEC-BLOCK]` 停下 ship，而 `standards` 发现在任何 tier 都不阻断，超时与读不出/畸形裁决亦然（它们不带 axes）；`ReviewGate='required'` 恢复旧强制闸（block 即停 ship，裁决持久化在 `.review/<branch>.json`）。

## 0. Reviewer stance (mandatory) · 评审者立场

- **Default to suspicion** · 默认怀疑: every reason must point to a **specific change** (file + rough location + why it violates). A "feels off" with no evidence is neither a block reason nor a pass reason.
- **Uncertain → block** · 不确定即 block: when information is insufficient to confirm safety/correctness, block and write the "evidence still needed" in the reason. Do **not** default to letting it through.
- **No self-exoneration** · 不自我开脱: after finding a real violation, do not downgrade it with "minor impact / probably fine / will fix later". If it should block, block.
- **Sweep the class, don't stop at the first hit** · 同类扫全、勿首错即停: when a finding is one instance of a **repeatable class** (a stale comment, an unanchored regex, one of N authoritative files left unsynced), search the rest of this diff for the remaining instances and report every same-class instance in this pass — do not report the most glaring one and leave the rest for a later round. Every omitted instance costs the author a full extra review round.
- **Exhaust the diff in one pass** · 单轮穷尽 (T66): beyond the same-class sweep, your reasons this round must be the **complete** finding list for this diff — every defect you can find, across all classes. In a follow-up round you may only judge (a) whether previously reported findings are fixed and (b) genuinely new/changed code; raising an issue that was already visible in an earlier round's diff and went unreported is a **review failure, not diligence**. Context (T68): this review is **advisory by default** (`ReviewGate` empty) — completeness in a single pass is precisely what makes one opinion useful; under `ReviewGate='required'`, deadlocked contentions go to human adjudication per the execution boundary's "two rounds of maker-checker deadlock → stop, human decides". · 单轮报全、勿分轮挤牙膏：本轮 reasons 须是对本 diff 的完整发现清单；后续轮只判前轮发现是否已修与真正新增的代码。 **The data behind this clause (T160/TD159)**: a follow-up round is now HANDED the prior round's findings. `review.ps1` reads `.review/<branch>.json` before its stale-verdict discard and, when that verdict names a DIFFERENT sha on this branch, injects its reasons as a bounded **data** block titled 「前轮已报发现」, announcing `[R3-FOLLOWUP]` with the count. Carried text is reviewer-authored and unsanitised, so it is framed as data exactly like the card and the diff - never as instructions. A verdict at the SAME sha is deliberately not carried: that is the round's own output, and feeding it back would let a reviewer agree with itself. So “judge only (a) fixed? and (b) new code” is now an instruction with evidence attached, not an appeal to memory the reviewer never had.
- **Judge only this diff** · 只判本次 diff: judge changes against the baseline branch; do not evaluate pre-existing history.
- **Honor the card** · honor 卡声明: the card's (`specs/tasks/<branch>.md`) `allow_paths` / boundary exceptions / notes are the authoritative source of the **explicitly approved scope**; opt-in exceptions in the card are not violations. Scope ≠ a waiver on correctness/quality. **The card you are handed is the BASE copy (T290)**, read with the sentinel `[R3-CARD-FROM-BASE] sha=<base>` from the same pinned baseline this rubric itself comes from - the copy the ship's scope gate, the computed tier and any `arbitration:` ruling all bind to, so a ruling or an amendment written there reaches you on the very next round instead of after the branch merges the base. Only when the baseline has no such card is the worktree copy used, announced as `[R3-CARD-FROM-WORKTREE]`.

## 1. Must-block dimensions (any hit → block) · 必须 block 的维度

1. **Out of scope** · 越界 · `axis: spec`: changes exceed the card's declared `allow_paths`. **File-level path membership is machine-decided (T146)**: the BLOCKING ship scope gate (`scripts/_scope.ps1`) ran to completion before you were invoked, so scope is settled and disagreeing with it is wrong by construction - that gate is the merge bar. Still yours: capability over-reach INSIDE an allowed file, which is #14.
2. **Hard boundaries** · 硬边界 · `axis: standards` (see `CLAUDE.md` "硬边界 / 关键不变量"): unauthorized **runtime** outbound network; auto-publish/release; writing login/session state; committing `.env` / auth files; relaxing the offline/determinism boundary that tests/CI established.
3. **Frozen contract/schema** · 冻结契约/schema · `axis: standards`: touching signatures/fields listed in `scripts/_config.ps1` `FrozenPaths` **without a version review** (the card not declaring "this card = the version review").
4. **License non-compliance** · 许可不合规 · `axis: standards`: introducing GPL/AGPL/LGPL static-linking/SSPL/EUPL or other copyleft, or any non-commercial / research-only / CC-BY-NC code · weights · data · assets (see `docs/LICENSE-POLICY.md`). **Dependency-licence identity is machine-decided (T146)**: `scripts/check-licenses.ps1` is BLOCKING and ran before you were invoked, so the declared licence of a dependency is settled. What remains yours is vendored or copied third-party SOURCE, which is #5.
5. **Non-original** · 非原创 · `axis: standards`: suspected third-party copyleft source snippets / plagiarism.
6. **Tests missing or fake** · 测试缺失或虚假 · `axis: spec`: no corresponding self-verifying test; the test is an empty file / fake assertion / vacuous pass (tests a transformation but lacks the input being transformed — see L19). **When the card carries an `acceptance:` list, judge against it** (T103): every numbered item needs a non-vacuous self-verifying test, and a listed item without one still blocks. A gap NOT on that list is reported as `[FOLLOW-UP]`, never as a block. Without an enumeration "missing" is decided against an open set, so each round can name another untested branch and the review never converges. No list means judge the whole diff, as before. Common shape to watch: a test that exists and passes still fails this dimension when its assertion surface is narrower than the contract - read the assertion against the contract, not merely for existence (L165).

## 2. Should-flag dimensions (block or note per severity) · 应当指出的维度

> **Conditional dimensions (T146)**: #13/#14/#15/#17 (those marked "only when") are assembled per round - `review.ps1` omits one when this diff and card cannot trigger it. Nothing is deleted; all stay live downstream. Routing **fails open**: an undecidable trigger CARRIES the dimension (a wrongly suppressed one is a silent hole; a wrongly carried one costs only attention). Not exhaustive - a schema change inside a here-string, or a dependency arriving via an untouched lockfile, is not decidable from these inputs.

7. **Traceability** · 可追溯性 · `axis: spec`: every changed line should trace to a card requirement; strip unrelated drive-by edits.
8. **Over-engineering / altitude** · 过度设计 · `axis: spec`: would a senior engineer find it over-abstracted / reinventing the wheel; point out simpler approaches. **Does the diff contain code the card did not ask for** - guards, wrappers, branches, abstractions traceable to no numbered `acceptance:` item, or absent a list, to no stated requirement? **The remedy for untraceable code is removal, not test coverage.** Where #6 and #8 both fit one construct, **#8 takes precedence**: report "delete this", not "test this". Without that precedence the two conflict silently and #6 wins, being the blocking-shaped one, and each added guard-plus-test enlarges what the next round scans. Pervasive untraceable code leans block.
9. **Error handling** · 错误处理 · `axis: standards`: do failure paths distinguish retryable/non-retryable; is there silent error-swallowing.
10. **Determinism** · 确定性 · `axis: standards`: any hidden non-determinism introduced (time/random/network/global state) that breaks CI reproducibility.
11. **Test organization/hygiene** · 测试组织/卫生 · `axis: standards`: editing existing code but creating a **parallel new test file** instead of extending the unit's existing tests, or test layout **not mirroring** the source → point it out and name the existing test file it belongs in.
12. **Structured logging/observability** · 结构化日志/可观测 · `axis: standards`: do critical paths/error branches have **structured logs** (request id / user id / key params) sufficient for an agent to **reconstruct the scene** from logs; no bare `print`; secrets redacted (see `docs/DELIVERY-OPS.md` §b). Block or note per severity.
13. **Data/persistence design** · 数据/持久层设计 · `axis: standards` (only when the change includes DB schema/migrations): business tables have audit fields (created_at/by, updated_at/by) and consistent soft-delete; **a soft-deleted table's unique index must include `deleted`** (omitting it makes re-inserting the same value impossible after delete = silent data corruption → lean block); money uses `DECIMAL` not `FLOAT`/`DOUBLE`; `status`/`state` has defined values + transitions + terminal states; reference fields are indexed, relations documented (logical FKs by default, no physical FKs across DB/service); **no business logic in triggers/stored-procedures/DB-events** (hidden side effects); indexes derive from query scenarios not arbitrary by-field; MySQL uses `utf8mb4`. **Data-corruption classes** (soft-delete unique index, money precision) lean block; the rest note per severity. Defaults adapt to the project stack (tool-agnostic); see `docs/lessons/database.md`.
14. **Scope fidelity / capability over-reach** · 范围保真 / 能力级越界 · `axis: spec` (only when the card has `non_goals`): does the diff implement a capability the card's `non_goals` (or the plan's "cut/deferred this version") **explicitly excluded** — the most common error of reviewer and implementer agents is not doing too little, but "doing extra on the side" (e.g. building a rating feature and tossing in likes/edit/moderation/image-upload). Complements **#1**: #1 judges "touched a **file** outside `allow_paths`"; #14 judges "built a capability the card **explicitly excluded**, inside allowed files." Hitting an explicitly listed `non_goal` → lean block; no `non_goals` listed → this dimension does not fire (don't presume scope).
15. **API-version correctness** · API 版本正确性 · `axis: standards` (only when the diff calls a third-party library API): does the code use an API that **does not exist or is deprecated in the version actually pinned** (lockfile/manifest) — hallucinated or stale usage written from memory rather than verified against version-correct docs? The implementer is responsible for verifying against the pinned version at **R2** (via Context7 MCP for that version, or `docs/references/*-llms.txt`); at review, flag calls whose signatures / params / imports look mismatched to the pinned **major** version. Uncertain whether an API exists in that version → note it and name the exact `library@version` to check (don't hand-wave). Tool-agnostic (L26): the standard is "verified against the **pinned** version's docs"; Context7 is the current default fetcher. Note per severity (clear version-mismatch that would fail at runtime → lean block).
16. **De-AI-slop / hand-of-an-engineer** · 去 AI 味 · `axis: standards` (applies to every code change): does the diff read like an experienced engineer wrote it to solve *this* problem, or like an LLM padding it to "look complete"? Concretely flag — **over-commenting** (per-line narration, or comments restating *what* the code does instead of *why*); **mechanical padding** (a simple operation exploded into needless intermediate variables/boilerplate — tidy but hollow); **over-long / multi-responsibility functions** (much over ~50 lines doing several things → name the split, unless splitting hurts readability); **house-style divergence** (a second style introduced instead of matching neighboring code). Complements #7 (drive-by edits), #8 (over-abstraction), #9 (defensive dead code / empty catch) — adds the comment / verbosity / function-shape / house-style lens they miss. Note per severity; a diff that is *pervasively* LLM-padded (not one stray comment) → lean block, citing the specific spots.
17. **Bugfix root-cause / not symptom** · bugfix 根因非表象 · `axis: spec` (only when the card is a bugfix / the diff repairs a defect): does the change fix the **root cause** or merely silence the **symptom**? Require the card's `diagnosis` field (or the PR body) to **name the cause** — why it broke, not just where it surfaced — and check whether **same-class callers / sites** share the same defect and are covered (a one-site patch for an N-site bug → lean flag). Complements **#6** (tests missing/fake): #6 asks "is there a regression test pinning the bug", #17 asks "was the *cause* found, or the symptom papered over". Guess-and-patch with no articulated cause, or a fix that visibly treats a symptom while the cause lives elsewhere → note per severity; a symptom-only patch that leaves the defect reachable → lean block. Not a bugfix card → this dimension does not fire (don't presume; a feature card needn't carry a diagnosis).

## 3. Output contract · 输出契约

The review returns exactly one line of JSON, structure matching `specs/verdict.schema.json`. **Write all `reasons` in English.** Emit **only** the two shapes below: the schema also declares fields the harness fills in while normalizing (`sha`, `branch`, `run_status`), and those are never the reviewer's to write.
- pass: `{"verdict":"pass","reasons":[],"axes":{"spec":{"verdict":"pass","reasons":[]},"standards":{"verdict":"pass","reasons":[]}}}`
- block: `{"verdict":"block","reasons":["[spec] <dimension #/name> @ <file:location> — <why it violates + how to fix>","[standards] ..."],"axes":{"spec":{"verdict":"block","reasons":["..."]},"standards":{"verdict":"pass","reasons":[]}}}`

**Two axes, never merged** · 两轴不合并 (T277 / ADR 0016 item 4): `spec` asks *does the diff do what the card closed*, `standards` asks *is the code sound*. Every dimension above carries its own `axis:` label and that label is the only mapping — put each finding on the axis its dimension names, state it once, and never rerank or soften one axis because the other came out clean. Top-level `verdict` is the **worst** of the two axes and whatever you wrote at the top level — the split can never soften your own verdict — and top-level `reasons` is both lists behind an `[spec]` / `[standards]` prefix, so a consumer that only reads those two fields sees exactly what it always saw. Measured cause: across 39 stored verdicts, dimension 6 alone was 20 of 34 findings and 17 of those hit code that already had a passing test — one axis was drowning the other in a single list. Consequence for the author: **only** an axis-`spec` block, and **only** on a Tier-S card, stops a ship (`scripts/task.ps1`, `[R3-SPEC-BLOCK]`); a `standards` finding is advisory at every tier, and so is a timeout or an unreadable verdict, which carry no axes at all. A verdict that omits `axes` is normalized into both axes carrying the top-level verdict, so a custom `ReviewCommand` backend that never learned the field still works.

**When we cannot agree** · 两轮不认可即人裁 (T285): `CLAUDE.md` already ends this - two rounds on one disagreement, then a person rules - but the ship could not READ that ruling, and on T279 this block came back **eight** times. A person writes an `arbitration:` entry on the BASE card, and `scripts/task.ps1` honours it only if all of it holds: well formed, `sha` equal to the sha THIS verdict was written at, `ruling: maker`, and two consecutive spec-block rounds in the same worktree's local review records. That verdict is advisory, printed as `[R3-SPEC-ARBITRATED]` and ledgered. The `.review/` records are gitignored working state, not committed audit evidence; durable, reviewable evidence is the exact-sha GitHub status/PR comment emitted by `-PostStatus`. **For you**: state a spec finding once and do not re-raise the same disagreement in a new form - the second round is where it stops being yours to decide.

Each block reason should include "**which dimension + where + how to fix**" so the verdict itself doubles as a fix prompt (error message as prompt).
每条 block reason 尽量含「违反哪条维度 + 在哪 + 怎么改」——让裁决本身可作修复提示。

## 4. Reviewer wall-clock budget · 评审者时间预算

The reviewer runs under a wall-clock timeout enforced by `review.ps1`. On timeout the process tree is killed and the verdict is a **fail-closed `block`** tagged `[R3-REVIEWER-TIMEOUT]` (§5). That block is a **harness budget signal, not a quality judgement about the diff** — do not read it as "the change is bad".

Budget precedence: `review.ps1 -TimeoutSec` > `_config.ps1` `ReviewTimeoutSec` > built-in 600s. The budget that actually won is announced on the reviewer's startup line as `[R3-TIMEOUT-BUDGET] <n>s`. That is a **different moment** from `[R3-REVIEWER-TIMEOUT]` (§5) and **not a block code**: the budget code says which budget is in force as the reviewer starts, the timeout code is raised only if that budget is later exceeded. Match on the code, never on the prose around it.

Actually running the repository's own checks to verify a diff is **legitimate and encouraged** reviewer behaviour. If that verification does not fit the budget, the correct fix is to **raise the budget** — never to ask the reviewer to verify less. Trading verification depth for pass rate weakens the very gate this rubric exists to enforce. A lightweight targeted entry also exists (T62/TD109③): `pwsh -File scripts/selftest.ps1 -Only {gate-id}` runs just the gates you name — comma-separated for multiple (`-Only 3,6`); valid ids `1`..`17`, `17t`, `17ac`, `17pre`, `17post` (gate 17's two regions — T118) and `17base` (umbrella ≡ 17pre+17post). Most gates finish in seconds; the heavy gates (15 and 17) run minutes. Its conclusion sentinel is `[SELFTEST-ONLY-PASS]`, deliberately distinct from the full-run `selftest: PASS` — a single filtered run is **never** the acceptance face; acceptance is full 17-gate coverage (a local parameterless run, or CI's shard union, all green — shard list's source of truth is the scaffold-selftest.yml matrix (T64/T65)). Note (ADR 0007): that workflow does **not** run on pull requests, so on a PR the local full run is the only 17-gate proof — reviewing a diff that touches scripts/hooks/workflows means asking for it, not assuming CI produced it. Use it to verify more within the budget, not to verify less.

**Intensity is a separate dial from this budget** (T301): `ReviewIntensityByTier` in `_config.ps1` keys a class — `adversarial` / `advisory` / `skip` — on the tier a card's `allow_paths` **compute**, announced as `[R3-INTENSITY]`, and it can only ever lower. The trade-off is recorded rather than assumed away: R3 has found real stale-card-text findings on doc-shaped cards (T278, T294), and a Tier-0 `skip` gives those up **by decision**. Raising that tier to `advisory` buys them back only for diffs this dial actually sees: `ReviewSkipWhen` is consulted first and exits, so a markdown-only, gate-free diff is routed away by content before intensity is resolved and prints no `[R3-INTENSITY]` — restoring a review for those means relaxing `ReviewSkipWhen`, not this map. Nothing here changes what a review that DOES run is asked to do: advisory-by-default (§0) is about what a verdict may block, this is about which diffs draw one.

评审者受 `review.ps1` 的 wall-clock 超时约束：超时即杀进程树、fail-closed 记 `block`（状态码 `[R3-REVIEWER-TIMEOUT]`，见 §5）——那是**预算信号，不是对 diff 的质量判断**。预算优先级：`-TimeoutSec` > `_config.ps1` 的 `ReviewTimeoutSec` > 内建 600s；真正生效的那个预算由评审者启动行以 `[R3-TIMEOUT-BUDGET] <n>s` 报出——它与 §5 的 `[R3-REVIEWER-TIMEOUT]` 是**两个时点**且**不是阻断码**：前者说「开跑时用的是哪个预算」，后者只在该预算随后被超出时才抬起。**按状态码匹配，别按周边措辞**。**评审者真跑一遍仓库自检来验证 diff 是正当且被鼓励的行为**；跑不完就调大预算，绝不是让评审者少验——拿核验深度换过闸率，就是弱化本 rubric 要守的那道闸。另有轻量定向入口（T62/TD109③）：`pwsh -File scripts/selftest.ps1 -Only {闸id}` 只跑点名的闸（多 token 逗号分隔如 `-Only 3,6`；合法 id `1`..`17`、`17t`/`17ac`/`17base`/`17pre`/`17post`；多数闸秒级，重闸（15/17）分钟级），结论哨兵 `[SELFTEST-ONLY-PASS]` 与全量 `selftest: PASS` 刻意不同——**单一滤过跑永远不是**验收面，验收 = 全 17 闸覆盖（本地无参全量，或 CI 分片并集全绿——T64/T65）；它是让你**在预算内验得更多**的工具，不是少验的理由。

## 5. Block states and recovery routes · 阻断态与恢复路由

Not every `block` is a quality judgement. Where the block is **harness-authored** — no usable verdict could be read, or a verdict was read but must not be trusted — `review.ps1` tags it with an **ASCII state code** so the log tells you which failure you have. All of them stay `block` (the gate never opens on an unclear verdict) but they route very differently. Since T188 the normalized verdict also carries a machine-readable **`run_status`** (`success` / `timeout` / `no_output` / `malformed` / `tool_error`) recording **how the run ended** rather than what it decided — producer-side only, with `verdict` itself staying exactly `{pass, block}`. That is the field separating *fix the diff* from *retry the reviewer*, and it keeps a reviewer outage from being counted as a quality round; the state-code-to-class mapping is in [`rubric-detail.md`](rubric-detail.md). Match on the **state code**, never on the prose — the prose is free to change, the code is the contract. Full routing notes, including the two look-alike read failures and what to do when a reviewer writes prose instead of JSON: [`rubric-detail.md`](rubric-detail.md).

`ReviewRoundCap=2` counts every unsuccessful attempt after the reviewer was actually invoked, including timeout/no-output/malformed/tool failures; setup failures before invocation and routed skips do not spend it. `run_status` keeps those causes distinguishable in history without changing the legacy throttle. At the cap, `[R3-ROUND-CAP]` stops before reviewer invocation for human adjudication. `review.ps1 -ResetRounds` clears only the local counter and exits without reviewing; round-indexed and local record files remain available for diagnosis.

> split rather than raise the ceiling). It is OPERATOR recovery routing, not reviewer criteria - the same
> reasoning T156 used when it moved this section's prose out. Match on the **state code**, never on prose.

## 6. What an advisory finding becomes afterwards (R5) · 意见发现的去向

Two rules, and they exist because a finding that merged anyway used to have no stated destination — so it became either a tech-debt row nobody could reproduce or a card nobody needed (TD245: five rounds, five findings, zero code defects).

- **A post-merge advisory finding becomes a tech-debt row only when it is `re-measured` on the merged tree and still holds as a code defect.** The re-measurement is the bar, not the reviewer's confidence: open the merged tree, run the thing, and record what you found. A finding that no longer reproduces there is closed by saying so in the card's R5 note — never carried forward as a row, because a row nobody can reproduce costs every later sweep and repays nothing.
- **A finding about card prose is fixed in that card's own R5 commit and never becomes a card.** Wording that misdescribes what shipped is a documentation defect of that card; the fix is an edit to it on the base branch, in the same commit that flips its `status`. Opening a follow-up card to rewrite a sentence is how a review round turns into a backlog item that outlives the thing it describes.

Neither rule applies to a `spec` block on a Tier-S card: that one is not advisory and never reaches R5 — the ship stopped.
