# Review Rubric (R3 second-model review decision standard) · 评审 Rubric

> EN: The 17-dimension rubric the R3 second-model reviewer (currently codex, via `scripts/review.ps1`) judges every PR against — six must-block dimensions (scope, hard boundaries, frozen contracts, license, originality, missing/fake tests) plus eleven should-flag ones — with a pinned adversarial stance: when uncertain, block. This file is injected verbatim into the reviewer prompt, so it IS the merge-gate decision standard.

> **English-first / bilingual** — this file is injected verbatim into `scripts/review.ps1`'s reviewer prompt **and** is edited per-project, so it is the one steering file an English-only team must be able to read and maintain. The Chinese is kept alongside for the original audience. Reviewers should emit their `reasons` in **English** (they are posted to GitHub PR status/comments).
>
> **Motivation** (Anthropic, *Harness Design for Long-Running Agentic Applications*): a reviewer agent naturally tends to **confidently praise mediocre output**, and after spotting a real problem **talks itself into "this is no big deal"** and lets it through. Countermeasure: upgrade "pass/block" from **free judgment** to **judgment against an explicit rubric + mandatory evidence**, and pin the reviewer's stance — **when uncertain, block; never find excuses for the author.**
> 动机：评审型 agent 天然倾向自信地夸奖平庸产出，并在发现真问题后说服自己「这没什么大不了」而放行。对策：把判定升级为「对照明确 rubric + 必须给证据」，并钉死立场——**不确定即 block，绝不替被审方找台阶。**
>
> Authoritative source of the standard fed to the reviewer; change decision dimensions here first. Ships downstream — projects extend §1 with their own hard-boundary / invariant clauses.
> 本文件是权威来源，改判定维度先改这里；随模板下发，下游按自己的「硬边界 / 关键不变量」补充 §1。
>
> **R3's nature — a deliberately accepted *non-deterministic* gate** · R3 的性质（有意接受的非确定闸）: R3 is a **second-model adversarial review that replaces the human approver** — NOT an "LLM-judge quality score". The scaffold's "deterministic gates only / a model judge is never a gate" axiom (see `docs/EVAL.md`) bans **subjective quality scoring** as a gate; it does **not** apply to R3, because replacing a human reviewer is inherently non-deterministic (a human approver isn't reproducible either). Trade-off: the verdict **can differ run-to-run**. **Spurious-block / flake path**: re-run `ship` with **no code change** (the model re-reviews), or fix per the `reasons` and re-ship; the verdict + reasons persist in `.review/<branch>.json`. So don't over-trust "all my gates are deterministic" for the one gate that blocks every merge — R3 is the deliberate exception.
> R3 是**第二模型对抗评审代替人工审批**，不是「LLM 质量打分」。脚手架「确定性闸 only / model-judge 永不当闸」禁的是**主观质量分**当闸，**不约束 R3**（代替人工 reviewer 本就非确定）。代价：裁决**跑跑可能不同**；**误 block 重审**：不改代码重跑 `ship`（评审会重跑）或按 reason 修后重 ship（裁决持久化在 `.review/<branch>.json`）。

## 0. Reviewer stance (mandatory) · 评审者立场

- **Default to suspicion** · 默认怀疑: every reason must point to a **specific change** (file + rough location + why it violates). A "feels off" with no evidence is neither a block reason nor a pass reason.
- **Uncertain → block** · 不确定即 block: when information is insufficient to confirm safety/correctness, block and write the "evidence still needed" in the reason. Do **not** default to letting it through.
- **No self-exoneration** · 不自我开脱: after finding a real violation, do not downgrade it with "minor impact / probably fine / will fix later". If it should block, block.
- **Sweep the class, don't stop at the first hit** · 同类扫全、勿首错即停: when a finding is one instance of a **repeatable class** (a stale comment, an unanchored regex, one of N authoritative files left unsynced), search the rest of this diff for the remaining instances and report every same-class instance in this pass — do not report the most glaring one and leave the rest for a later round. Every omitted instance costs the author a full extra review round.
- **Judge only this diff** · 只判本次 diff: judge changes against the baseline branch; do not evaluate pre-existing history.
- **Honor the card** · honor 卡声明: the card's (`specs/tasks/<branch>.md`) `allow_paths` / boundary exceptions / notes are the authoritative source of the **explicitly approved scope**; opt-in exceptions in the card are not violations. Scope ≠ a waiver on correctness/quality.
- **Never enlarge the card** · 不得给卡加范围 (**a block reason must be actionable inside this card**): if remedying a finding would require editing a file **outside** the card's `allow_paths`, or would require building a capability **inside** the card's `non_goals`, it is **not a block reason for this card**. Report it in `reasons` prefixed `[FOLLOW-UP]` while still returning `pass` if nothing else blocks; the orchestrator opens a separate card. Rationale (measured on this repo): a correctly scoped card — "empty project compiles green" — took **9 review rounds** and grew to 23 files / 1017 insertions because successive rounds pushed licence-audit work into a toolchain card; it then had to be split, and the split card took **12 more rounds**. A card is a fixed contract; a reviewer that can extend it makes scope a variable, and the loop stops converging. **This does not weaken #1**: #1 blocks the *author* for touching files outside `allow_paths` — this clause forbids the *reviewer* from demanding work there.
- **Judge against the card's declared DoD, not a universal one** · 按卡片自己的 DoD 判: the card's `dod_command` / `dod_assert` define what "verified" means **for this card**. Where a card declares a non-unit-test acceptance shape — a spike, a throwaway walking skeleton, a manual on-device walkthrough — dimension **#6** is satisfied by **that declared evidence**, not by unit tests the card deliberately excluded. Demanding a different acceptance shape than the card declares is a `[FOLLOW-UP]` on the card's design, not a block on the diff. **Uncertain → block still holds** for anything inside the card's own declared scope.

## 1. Must-block dimensions (any hit → block) · 必须 block 的维度

1. **Out of scope** · 越界: changes exceed the card's declared `allow_paths`.
2. **Hard boundaries** · 硬边界 (see `CLAUDE.md` "硬边界 / 关键不变量"): unauthorized **runtime** outbound network; auto-publish/release; writing login/session state; committing `.env` / auth files; relaxing the offline/determinism boundary that tests/CI established.
3. **Frozen contract/schema** · 冻结契约/schema: touching signatures/fields listed in `scripts/_config.ps1` `FrozenPaths` **without a version review** (the card not declaring "this card = the version review").
4. **License non-compliance** · 许可不合规: introducing GPL/AGPL/LGPL static-linking/SSPL/EUPL or other copyleft, or any non-commercial / research-only / CC-BY-NC code · weights · data · assets (see `docs/LICENSE-POLICY.md`).
5. **Non-original** · 非原创: suspected third-party copyleft source snippets / plagiarism.
6. **Tests missing or fake** · 测试缺失或虚假: no corresponding self-verifying test; the test is an empty file / fake assertion / vacuous pass (tests a transformation but lacks the input being transformed — see L19).

## 2. Should-flag dimensions (block or note per severity) · 应当指出的维度

7. **Traceability** · 可追溯性: every changed line should trace to a card requirement; strip unrelated drive-by edits.
8. **Over-engineering / altitude** · 过度设计: would a senior engineer find it over-abstracted / reinventing the wheel; point out simpler approaches.
9. **Error handling** · 错误处理: do failure paths distinguish retryable/non-retryable; is there silent error-swallowing.
10. **Determinism** · 确定性: any hidden non-determinism introduced (time/random/network/global state) that breaks CI reproducibility.
11. **Test organization/hygiene** · 测试组织/卫生: editing existing code but creating a **parallel new test file** instead of extending the unit's existing tests, or test layout **not mirroring** the source → point it out and name the existing test file it belongs in.
12. **Structured logging/observability** · 结构化日志/可观测: do critical paths/error branches have **structured logs** (request id / user id / key params) sufficient for an agent to **reconstruct the scene** from logs; no bare `print`; secrets redacted (see `docs/DELIVERY-OPS.md` §b). Block or note per severity.
13. **Data/persistence design** · 数据/持久层设计 (only when the change includes DB schema/migrations): business tables have audit fields (created_at/by, updated_at/by) and consistent soft-delete; **a soft-deleted table's unique index must include `deleted`** (omitting it makes re-inserting the same value impossible after delete = silent data corruption → lean block); money uses `DECIMAL` not `FLOAT`/`DOUBLE`; `status`/`state` has defined values + transitions + terminal states; reference fields are indexed, relations documented (logical FKs by default, no physical FKs across DB/service); **no business logic in triggers/stored-procedures/DB-events** (hidden side effects); indexes derive from query scenarios not arbitrary by-field; MySQL uses `utf8mb4`. **Data-corruption classes** (soft-delete unique index, money precision) lean block; the rest note per severity. Defaults adapt to the project stack (tool-agnostic); see `docs/lessons/database.md`.
14. **Scope fidelity / capability over-reach** · 范围保真 / 能力级越界 (only when the card has `non_goals`): does the diff implement a capability the card's `non_goals` (or the plan's "cut/deferred this version") **explicitly excluded** — the most common error of reviewer and implementer agents is not doing too little, but "doing extra on the side" (e.g. building a rating feature and tossing in likes/edit/moderation/image-upload). Complements **#1**: #1 judges "touched a **file** outside `allow_paths`"; #14 judges "built a capability the card **explicitly excluded**, inside allowed files." Hitting an explicitly listed `non_goal` → lean block; no `non_goals` listed → this dimension does not fire (don't presume scope).
15. **API-version correctness** · API 版本正确性 (only when the diff calls a third-party library API): does the code use an API that **does not exist or is deprecated in the version actually pinned** (lockfile/manifest) — hallucinated or stale usage written from memory rather than verified against version-correct docs? The implementer is responsible for verifying against the pinned version at **R2** (via Context7 MCP for that version, or `docs/references/*-llms.txt`); at review, flag calls whose signatures / params / imports look mismatched to the pinned **major** version. Uncertain whether an API exists in that version → note it and name the exact `library@version` to check (don't hand-wave). Tool-agnostic (L26): the standard is "verified against the **pinned** version's docs"; Context7 is the current default fetcher. Note per severity (clear version-mismatch that would fail at runtime → lean block).
16. **De-AI-slop / hand-of-an-engineer** · 去 AI 味 (applies to every code change): does the diff read like an experienced engineer wrote it to solve *this* problem, or like an LLM padding it to "look complete"? Concretely flag — **over-commenting** (per-line narration, or comments restating *what* the code does instead of *why*); **mechanical padding** (a simple operation exploded into needless intermediate variables/boilerplate — tidy but hollow); **over-long / multi-responsibility functions** (much over ~50 lines doing several things → name the split, unless splitting hurts readability); **house-style divergence** (a second style introduced instead of matching neighboring code). Complements #7 (drive-by edits), #8 (over-abstraction), #9 (defensive dead code / empty catch) — adds the comment / verbosity / function-shape / house-style lens they miss. Note per severity; a diff that is *pervasively* LLM-padded (not one stray comment) → lean block, citing the specific spots.
17. **Bugfix root-cause / not symptom** · bugfix 根因非表象 (only when the card is a bugfix / the diff repairs a defect): does the change fix the **root cause** or merely silence the **symptom**? Require the card's `diagnosis` field (or the PR body) to **name the cause** — why it broke, not just where it surfaced — and check whether **same-class callers / sites** share the same defect and are covered (a one-site patch for an N-site bug → lean flag). Complements **#6** (tests missing/fake): #6 asks "is there a regression test pinning the bug", #17 asks "was the *cause* found, or the symptom papered over". Guess-and-patch with no articulated cause, or a fix that visibly treats a symptom while the cause lives elsewhere → note per severity; a symptom-only patch that leaves the defect reachable → lean block. Not a bugfix card → this dimension does not fire (don't presume; a feature card needn't carry a diagnosis).

## 3. Output contract · 输出契约

The review returns exactly one line of JSON, structure matching `specs/verdict.schema.json`. **Write all `reasons` in English.**
- pass: `{"verdict":"pass","reasons":[]}`
- block: `{"verdict":"block","reasons":["<dimension #/name> @ <file:location> — <why it violates + how to fix>", "..."]}`

Each block reason should include "**which dimension + where + how to fix**" so the verdict itself doubles as a fix prompt (error message as prompt).
每条 block reason 尽量含「违反哪条维度 + 在哪 + 怎么改」——让裁决本身可作修复提示。

## 4. Reviewer wall-clock budget · 评审者时间预算

The reviewer runs under a wall-clock timeout enforced by `review.ps1`. On timeout the process tree is killed and the verdict is a **fail-closed `block`**. That block is a **harness budget signal, not a quality judgement about the diff** — do not read it as "the change is bad".

Budget precedence: `review.ps1 -TimeoutSec` > `_config.ps1` `ReviewTimeoutSec` > built-in 600s.

Actually running the repository's own checks to verify a diff is **legitimate and encouraged** reviewer behaviour. If that verification does not fit the budget, the correct fix is to **raise the budget** — never to ask the reviewer to verify less. Trading verification depth for pass rate weakens the very gate this rubric exists to enforce.

评审者受 `review.ps1` 的 wall-clock 超时约束：超时即杀进程树、fail-closed 记 `block`——那是**预算信号，不是对 diff 的质量判断**。预算优先级：`-TimeoutSec` > `_config.ps1` 的 `ReviewTimeoutSec` > 内建 600s。**评审者真跑一遍仓库自检来验证 diff 是正当且被鼓励的行为**；跑不完就调大预算，绝不是让评审者少验——拿核验深度换过闸率，就是弱化本 rubric 要守的那道闸。

### 4.1 Complete-diff budget before reviewer invocation · 唤起评审者前的完整 diff 预算

`review.ps1` first measures the pinned `base...HEAD` diff without truncation. A review may start only when `additions + deletions <= 1000` **and** the unified diff is `<= 60000` characters. `task.ps1 ship` runs the identical path with `-SizeOnly` before push/PR; manual review repeats it. CLI limits may only be tightened, never raised.

评审只在真实 `additions + deletions <= 1000` **且**未截断 unified diff `<= 60000` 字符时启动。`ship -SizeOnly` 在 push/开 PR 前走同一路径，手工 R3 再复核；命令行只能收紧上限。三种失败都 fail-closed，其中超限必须拆成可独立验证的有序子卡，不能靠扩大 `allow_paths` 或阈值绕过。

## 5. Block states and recovery routes · 阻断态与恢复路由

Not every `block` is a quality judgement. Where the reviewer ran to completion but **no usable verdict could be read from its output**, `review.ps1` tags the block with an **ASCII state code** so the log tells you which failure you have and what to do about it. The first four codes below are exactly that family; the remaining nine rows cover different moments and are marked as such. They do **not** cover every operational block: the wall-clock timeout (§4), a non-zero exit paired with `pass`, a stale-SHA verdict, and baseline/rubric resolution failures still emit untagged English reasons, while diff argument/command/size/numstat failures use the dedicated rows below. All of them stay `block` — the gate never opens on an unclear verdict — but they route very differently. Within this family, match on the **state code**, never on the English prose (the prose is free to change; the code is the contract).

| State code | What happened | Route |
|---|---|---|
| `[R3-OUTPUT-UNREADABLE]` | The verdict output path exists but could not be read as a file — it may be a directory, locked, or permission-denied. Distinct from "nothing was written": here something occupies the path. | Inspect the path named in the reason and whatever holds or replaced it, then re-run ship. |
| `[R3-NO-OUTPUT]` | Reviewer exited without writing a verdict file, or wrote one that is empty or whitespace-only. No review result was captured — a custom backend may have reviewed and simply failed to write the file. | Backend crashed / was killed, or a custom `ReviewCommand` never honoured `$env:REVIEW_OUT`. Fix the backend, re-run ship. |
| `[R3-NO-VERDICT-JSON]` | Reviewer **did** write output, but it holds no JSON verdict — prose instead of the schema. This **may** be a backend safety-classifier refusal or mid-stream pause; it may equally be an adverse review written as prose, or an unrelated backend error. | **Read the preserved raw reviewer output in `.review/<branch>.raw.txt` first — it decides which case you are in.** (1) Refusal/pause → re-run ship, these are often transient. (2) Recurring on a security-shaped diff → point `ReviewCommand` at a second independent backend (this gate is backend-agnostic by design) or escalate to human adjudication. (3) Actually review feedback → fix the diff; do not re-run until it passes. (4) Never reword the card to dodge the classifier. |
| `[R3-BAD-VERDICT-JSON]` | A JSON object was produced but no usable `verdict` field could be read from it — parse failure, missing `verdict`, non-string `verdict`, or a value outside the case-sensitive enum `{pass,block}`. Runtime enforcement covers the `verdict` field only (it alone decides merge); the rest of `specs/verdict.schema.json` is checked statically by selftest gate 6, not here. | Backend emitted structured output that violates `specs/verdict.schema.json`. Fix the backend's output contract; for the built-in codex path, re-run ship. |
| `[R3-VERDICT-WRITE-FAILED]` | The verdict itself was decided, but the normalized verdict file could not be written, so this run left no auditable record of its own decision. Raised **after** the decision, and it overrides a `pass`. | Inspect the verdict path and whatever occupies or locks it (often the same cause as `[R3-OUTPUT-UNREADABLE]`), then re-run ship. |
| `[R3-REVIEW-DIR-UNSAFE]` | The verdict artifact path itself (the `<branch>.json` leaf), the round-counter path (`<branch>.rounds`, checked again at its own write point because a link can be planted *during* the review), the `.review` directory, or any of their ancestors is a symbolic link or reparse point. Every artifact this gate writes or deletes there — and everything the reviewer subprocess writes to `REVIEW_OUT` — would be redirected outside the worktree, so the gate refuses to proceed. Raised fail-closed at whichever of two checkpoints detects it: at startup (before any filesystem action), or immediately before invoking the reviewer — by then the `.review` directory may already exist from this run, but no further artifact operation occurs and the reviewer is not invoked. | Treat as a tampering signal: find out who placed that link in the reviewed worktree. The gate modified nothing after detection (at most an empty `.review` directory was created earlier in the run); remove the link and re-run ship. |
| `[R3-ROUND-CAP]` | **Not a judgement on this diff at all — a livelock stop.** This branch has already accumulated `ReviewRoundCap` block verdicts (`scripts/_config.ps1`, default 2), so the reviewer was **not invoked** this run. Raised before any reviewer call, so it costs seconds rather than a full review budget. Still `block`, still exit non-zero: capping rounds stops the spend, it never approves anything. | A human adjudicates — that is the point of the cap, and it is the rule `CLAUDE.md` already stated ("two rounds of mutual disagreement, then a human decides"). Three routes: (1) the finding needs work outside this card's `allow_paths` or inside its `non_goals` → open a follow-up card, leave this card alone; (2) the finding is real → fix it, then `review.ps1 -ResetRounds` to clear the counter and re-run; (3) the card itself is too large → split it. The counter lives at `.review/<branch>.rounds` and dies with the worktree. Set `ReviewRoundCap = 0` to disable capping. Never bypass with `--no-verify`. |
| `[R3-RAW-SAVE-FAILED]` | **Console diagnostic, not a verdict state.** Carries the OS-localized reason the raw-response artifact could not be written; the verdict is decided by `[R3-NO-VERDICT-JSON]` above, whose reason already states truthfully that the raw text is unavailable. Printed rather than posted because its wording is locale-dependent. | Read it in the ship log to see why the write failed (permissions, occupied path, full disk), then fix that and re-run ship. |
| `[R3-DIFF-TOO-LARGE]` | The complete pinned diff exceeds 1000 changed lines or 60000 characters; no reviewer ran and no round was consumed. | Split the card into ordered, independently verifiable units. |
| `[R3-DIFF-COMMAND-FAILED]` | A pinned diff command failed, so size and review input are not trustworthy. | Repair the repository, baseline, or diff driver, then rerun. |
| `[R3-DIFF-NUMSTAT-INVALID]` | Diff size contains an unclassifiable `--numstat` row. | Inspect the diff driver/output; unknown size never passes. |
| `[R3-DIFF-ARGS-INVALID]` | Mutually exclusive diff-budget operations were requested together (currently `-SizeOnly` with `-ResetRounds`). | Run one operation at a time; reset is not a successful size measurement. |
| `[R3-HEAD-MISMATCH]` | The caller pinned the commit it had already measured (`-ExpectHead`), but the reviewed worktree's `HEAD` is a different commit — or the pinned value is not a 40-hex OID. A branch ref alone cannot detect this: checking out another branch, or detaching `HEAD`, leaves `refs/heads/<TaskId>` pointing at the measured commit while `HEAD` walks away, so the commit that gets merged and the commit that got reviewed are not the same one. Raised before the round counter and before the reviewer is invoked, so no round is consumed. | Identity mismatch, not review feedback. Return the worktree to the measured commit (`git -C <worktree> checkout <TaskId>`), or re-run `-Phase ship` so every gate re-measures the current `HEAD`. Never widen the check to the branch ref alone. |

`[R3-VERDICT-WRITE-FAILED]` differs from the other four in *when* it is raised: the first four say no usable verdict could be read **from the reviewer**, whereas this one says the harness could not persist the verdict it had already decided. It is nonetheless a block state, and it **overrides a `pass`** — a verdict that cannot be persisted leaves no auditable record, and an unauditable approval is not an approval. Failing closed here matches the pre-existing behaviour, where an unwritable verdict path aborted the script outright.

The `[R3-NO-VERDICT-JSON]` reason does **not** inline what the reviewer wrote; it preserves the reviewer's raw response verbatim at `.review/<branch>.raw.txt` and points you there. If that write fails, the reason says so explicitly instead of pointing at a file that is not there. (The verdict file itself is overwritten with the normalized verdict, so the raw text is kept in a separate artefact.) That text is reviewer-controlled and derives from a model that just read an attacker-influenceable diff, so embedding it safely (sanitising, encoding, and making the state codes unforgeable) is handled separately in upstream scaffold TD96.

并非每个 `block` 都是质量判断（另有一条**不带码**的防御性兜底串，按现有分支不可达，故不列为契约）。**评审者跑完了、但从它的输出里读不出可用裁决**时，`review.ps1` 打一枚 ASCII 状态码，让日志自己说清是哪种故障、该怎么办。下表**前四行**才是这一族，其余九行覆盖另外的时点/性质；表中状态仍不覆盖全部运行态阻断——超时（§4）、非零退出却报 pass、陈旧 sha、基线/rubric 解析失败仍用不带码的英文 reason，diff 参数/命令/体量/numstat 失败则使用下表专属码。所有状态**一律仍 block**（裁决不明就不放行），但出路完全不同。其中 `[R3-OUTPUT-UNREADABLE]` 与 `[R3-NO-OUTPUT]` 易混却指向相反的排查方向：前者是**路径被占/读不了**（去查是谁占了那个路径），后者是**根本没写**（去查后端）——把读故障静默吞成「没写」正是本节要治的误导。**按状态码匹配，别按英文措辞**——措辞可改，状态码才是契约。其中 `[R3-NO-VERDICT-JSON]`（评审者干净退出、文件在、里面是散文）**可能**是分类器拒答/暂停，**也可能**是评审者把否定意见写成了散文、或后端吐了个无关错误——**先读 `.review/<branch>.raw.txt`（另存的评审者原文）再判**，别预设它与你的 diff 无关：若那段其实是评审意见，正确反应是**改 diff**，不是重跑到过闸为止；确属拒答/暂停时才走重跑 / 换第二后端 / 上人裁，**绝不是改卡措辞去骗分类器**，也绝不是 `--no-verify`。`[R3-BAD-VERDICT-JSON]` 则是「有 JSON 但读不出可用 verdict」的同类四支（解析失败 / 缺 verdict / verdict 非字符串 / 枚举不符）。**运行期只强制 verdict 字段**（唯一决定放不放行的字段）；schema 其余约束（reasons 须字符串数组 / 禁额外字段 / sha·branch 须字符串）由 selftest 闸 ⑥ 在产出侧静态机检，不在此处运行期校验。`[R3-VERDICT-WRITE-FAILED]` 与前四枚的差别在**何时抬起**：前四枚说的是「从评审者那儿读不出可用裁决」，它说的是「裁决已经定了、但 harness 存不下来」。它同样是阻断态，且**会覆盖 `pass`**——存不下来就没有可复核的记录，而不可复核的放行不算放行。这与基线行为一致：从前裁决路径写不进去时脚本直接中止（非零退出＝不放行），故这里必须 fail-closed，不能因为「已经 catch 了异常」就顺势放行。

`[R3-NO-VERDICT-JSON]` 的 reason **不内联**评审者原文，只把原文另存为 `.review/<branch>.raw.txt` 并指向它（裁决文件本身会被规范化裁决覆盖，故原文另放一份）；**若另存失败，reason 会如实说明原文不可得**，不会再指你去读一个不存在的文件。那段文本由评审者控制、且源自刚读过攻击者可影响 diff 的模型，**如何安全内联**（消毒 / 编码 / 让状态码不可伪造）另立加固卡；该历史债项来自上游脚手架的 TD96。
